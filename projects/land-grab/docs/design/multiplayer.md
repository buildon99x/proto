# 멀티플레이 — 한 화면과 온라인

서버를 짓게 될 때의 설계는 [io-server.md](io-server.md) 에 따로 있다.

## 1. 지금 되는 것: 한 화면 로컬 멀티 (파티 모드)

한 기기·한 키보드에서 **2~4명**이 함께 한다. 서버가 필요 없어 기존 배포 구조 그대로 돌아간다.

| 자리 | 키 | 색 |
| --- | --- | --- |
| P1 | 방향키 · 숫자패드 | 청록 |
| P2 | W A S D | 주황 |
| P3 | I J K L | 보라 |
| P4 | T F G H | 연두 |

왼쪽부터 WASD · TFGH · IJKL · 방향키 순으로 앉으면 팔이 겹치지 않는다.
1번 자리는 싱글 플레이와 같은 방향키라, 혼자 할 때 조작이 바뀌지 않는다.
혼자일 때만 1번 자리가 WASD 도 같이 받는다.

규칙 차이는 딱 하나다.

- **혼자**: 목숨 3개. 다 잃으면 그 자리에서 판이 끝난다. AI 수는 난이도가 정한다.
- **여럿**: 목숨 제한 없음. 항상 4명이 되도록 빈 자리를 AI 가 채우고, 90초를 끝까지 간다.
  한 사람이 목숨을 잃어서 판이 끝나면 나머지 사람들의 90초가 사라지기 때문이다.

화면도 인원에 따라 바뀐다. 여럿이면 1인용 지표(내 점유율·점수·킬·목숨)를 감추고
순위표가 주 계기판이 된다. 보드 위의 사람 말에는 `P1`~`P4` 배지가 붙고,
십자 조준선은 혼자일 때만 그린다 — 넷이 그으면 화면이 격자무늬가 된다.

## 2. 이 문서가 처음에 잘못 적은 것

여기에는 원래 "저장소의 `static-artifact` 제약 때문에 온라인이 불가능하다"고
적혀 있었다. **틀렸다.** 근거로 든 것을 다시 확인한 결과다.

- 레지스트리 스키마는 서버와 무관하다. 서버는 레지스트리에 등록되지 않는다.
- 워크스페이스 글롭이 `projects/*/app` 이라 `projects/land-grab/server/` 는
  pnpm 설치에도 Vercel 빌드에도 들어가지 않는다.
- 클라이언트는 그대로 `static-artifact` 로 런처에 남는다.

실제로 필요했던 것은 스키마 변경이 아니라 **"서버 프로세스를 어디에 둘 것인가"**
하나였다. Render 로 정했고, 서버는 지어져 있다 —
[io-server.md](io-server.md) §5, [render-deploy.md](render-deploy.md).

## 3. 온라인으로 가는 선택지

| 안 | 서버 | 작업량 | 가장 큰 문제 |
| --- | --- | --- | --- |
| A. 로컬 멀티 | 없음 | **완료** | 같은 자리에 모여야 한다 |
| B. P2P + 수동 코드 교환 | 없음 | 중 | 접속 코드를 복사해 상대에게 보내야 한다 |
| C. P2P + 공개 시그널링 | 외부 의존 | 중 | 남의 서버에 접속 성사를 맡긴다. 사내 네트워크 정책에 막힐 수 있다 |
| D. 전용 WebSocket 서버 | 필요 | 대 | **채택.** 운영 대상이 생긴다. 재배포하면 세계가 초기화된다 |

### B·C·D 가 공통으로 요구하는 것

지금 시뮬레이션은 **한 대에서만 맞으면 되는** 구조다. 온라인이 되려면 세 가지가 필요하다.

1. **결정적 시뮬레이션.** 엔진 자체는 시드를 받으면 결정적이지만,
   `AiController` 가 앱에서 `Math.random` 으로 돈다. 서버는 시드 난수를 넣어 쓴다(완료).
2. **권위의 소재.** 가장 싼 길은 호스트 권위다 — 한 쪽이 시뮬레이션을 돌리고
   나머지는 입력만 보내고 상태를 받는다. 입력이 칸 경계에서만 반영되는 이 게임의 규칙이
   여기에 유리하다. 보낼 것이 초당 6회, 방향 하나뿐이다.
3. **지연 보정.** splix 는 600ms / 5칸까지 되돌리기를 허용한다
   (`docs/design/splix-analysis.md` §1). 같은 장치가 필요하다.

보드가 `60 × 60` 이라 전체 상태가 3,600바이트다. 20Hz 로 통째로 보내도 72KB/s 다.
델타 없이 전체 스냅샷을 보내도 되는 크기라, 네트워크 코드 자체는 splix 보다 훨씬 단순해진다.

### 추천

**당장은 A 로 충분하고, 다음은 D 가 옳다.**

B 는 "접속 코드를 복사해서 상대에게 보내세요"가 되는데, 캐주얼 게임에서 그 한 단계가
사람을 다 떨군다. C 는 남의 인프라에 의존해 언제 끊길지 모르는 데다, 이 저장소는
프로토타입을 오래 살려 두는 곳이라 맞지 않는다.

D 로 가려면 저장소 차원의 결정이 먼저다 — `runtime` 에 값을 하나 더 열고,
게임 서버를 어디에 둘지 정해야 한다. 그 결정 없이 코드를 먼저 쓰면
`pnpm validate:projects` 부터 막힌다.
