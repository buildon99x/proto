# Mace recovery movement: isolated candidate

This document records isolated-stage evidence. Subsequent canonical integration
and full-suite verification are recorded in `attack-recovery-integration.md`.

Date: 2026-10-10 UTC. Node v24.19.0.

## Brief and authority

Normal-input review reported that holding basic attack can leave the hero unable
to walk. This candidate changes only `app/src/combat.js`: movement eligibility and
accurate movement bookkeeping during basic-attack recovery. It remains an isolated, unpublished source proposal.

The recovered brief, specification and requirements provenance were read without
modifying them. The existing base mace duration (0.52 s), contact fraction (35%),
and this recovery-movement rule are authored Emberwatch decisions. Original-game
movement/cancellation behavior remains UNKNOWN. No inference about the original
mechanic or balance quality follows from these tests. The canonical plan's local
byte-identical materialization is still recorded as unavailable in the recovered
requirements provenance; this work did not retry that transfer.

## Implemented contract

The existing movement block now runs when there is no action, or the action is
`mace_swing` and has already fired. Movement is still evaluated before
`resolveAction`. Consequently:

- Windup and the exact contact segment retain the planted origin.
- The next simulation segment may walk while the mace finishes recovery. An
  external frame split at contact may contain such a later segment.
- The action object, frozen spec, angle, castId, duration, elapsed progression,
  contact bookkeeping and full recovery debt remain intact. Walking does not
  cancel the action, shorten its duration or buy a free new attack.
- Explicit skill handling still precedes held basic attack. The existing 0.18 s
  single-slot buffer and guard/opposite-movement/inclusive-90-degree cancellation
  rules remain in force. Queued skills start once after recovery.
- Existing movement normalization, speed, slow/stun behavior, wall collision,
  block delay, charge, hammer and Onslaught movement rules are retained.
- A detached locomotion measurement uses the existing actual-displacement,
  alive/dash and movement-noise checks. Only its `moving` and existing
  distance-derived `walk` accumulator return to the real hero; its temporary
  angle, gait phase and footstep events do not. The actual action is never
  removed or replaced, even temporarily.
- Recovery movement from an earlier simulation segment remains visible in the
  outer frame when a later segment begins the next attack or queued skill.
  The following stationary frame resets `moving`; death cannot retain it.
- No HP, range, attack-speed, movement-speed, resource, cooldown or difficulty
  constant was changed. Guard cannot activate early. No dodge was added.
- `battleReport` still stores the entire remaining action debt. Main menu,
  blur/hidden safety and committed runtime synchronization retain the live mace
  object; reload keeps the old debt-only recovery contract rather than replaying
  a saved contact.

Production patch: `attack-recovery-movement-source.patch`, generated by plain
text diff against the recovered source. Gameplay edits are limited to the recovery movement gate, reuse of existing
locomotion measurement without changing action animation, and retaining earlier
recovery movement across segments of one outer frame. No Git command was used.

## Integrity and outstanding limits

Only this task's `combat.js`, two new test files, and `docs/attack-recovery-*`
files were written. None of the 178 recovered existing test/support/fixture
files was edited or removed by this task. At 15:38 UTC all 178 were byte-identical
to the recovered source. At 15:40 UTC 177/178 remained identical: the separate
UI owner had also updated the original `portable-checkpoint-ui.test.mjs`.
`attack-recovery-integrity.json` records both observations. The recovered source
is concurrently changing: a separate `portable-checkpoint-ui.js` edit appeared
in the original after the isolated copy was made. This candidate retains that file's untouched earlier bytes; the
UI change is not part of this patch. Do not replace an evolving source tree with
the whole candidate directory. Integrate only the small combat patch and the two
new tests, then rerun checks in the integration target.

The existing `advanceLocomotion` treats an action as an animation lock. The
candidate now measures recovery walking on a detached actor, retaining only
`moving` and `walk` on the real actor. The original movement-noise threshold
(0.001 world units), collision displacement and distance normalization remain
shared rather than being independently retuned. Run phase and footstep audio do
not advance, and the motion renderer still prioritizes the retained attack.

The main frame's `walkTime` now counts recovery-moving frames, including frames
whose later segment starts another attack. This retains its established
whole-frame convention: a mixed 0.05 s frame is counted once as 0.05 s, even if
only 0.02 s was recovery walking. It is not a precise subframe moving-time meter.
The `walk` accumulator follows actual traveled distance instead of attempted
speed or full-frame time. No `main.js`, motion, visual or save schema was changed.

The retained recovery pose may still visibly slide because no new gait or
footstep sound was added. Loaded-motion action priority is covered by tests;
native visual/audio review and the missing-motion-asset fallback remain
unverified. These are separate from the now-tested movement accounting.

Normal-input combat feel, retreat/damage-avoidance balance, moving-target
interactions and mixed enemy pressure still need representative play review.
No claim of improved overall difficulty, full campaign acceptance, or complete
regression safety is made. Publication and full-aggregate checks remain
integration-owner decisions.
