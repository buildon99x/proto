# 설계 검토 — 사망 기록 수집과 밸런스 조정 (구현 전)

> 요청: "사용자 플레이 중 죽은 위치를 서버에 기록했다가 나중에 개발자가 확인하고
> 밸런스를 조정할 때 활용." 이 문서는 그 요청을 검토하고 구현 가능한 수준으로
> 구체화한 것이다. 코드는 아직 없다.

## 결론

**만들 가치가 있다. 다만 "죽은 위치"를 그대로 저장하면 틀린 곳을 고치게 된다.**

이 프로젝트는 난이도를 이미 수치로 안다 — 솔버가 재는 생존 회랑 여유(ms)다.
사망 기록이 새로 주는 것은 난이도가 아니라 **솔버의 수치가 사람의 체감과 어디서
어긋나는가**이고, 그 어긋남만이 지금 측정 불가능한 값이다. 그러므로 스키마도 집계도
"솔버 회랑과 대조 가능한 형태"로 설계해야 하고, 그것이 이 문서의 대부분이다.

권고안은 네 층으로 나뉜다.

| 층 | 무엇 | 위험 |
|---|---|---|
| 수집 | 런 결말(사망·클리어·이탈) 이벤트를 클라이언트에서 만든다 | 여기에 설계 위험이 전부 몰려 있다 |
| 전송 | 배치 + `sendBeacon`, 실패 시 localStorage 큐 | 낮음. 재시도 마찰만 건드리지 않으면 된다 |
| 저장 | 런처의 Next 라우트 핸들러 + 외부 append 스토어 | 레포 최초의 백엔드다. 벤더 의존이 생긴다 |
| 해석 | 오프라인 분석기가 솔버로 코스를 재구성해 판정 | 여기가 실제 산출물이다 |

**순서는 수집 → 해석 → 전송 → 저장을 권한다.** 서버는 전송 계층을 갈아 끼우는
일이고, 위험은 전부 스키마와 해석에 있다. 스키마가 틀린 채로 서버가 먼저 서면
버려야 하는 데이터가 쌓인다. 1단계는 `exportMeta` 옆에 내보내기 버튼 하나로
끝나고 인프라가 0이며, 테스터 3명 규모의 중단 판정에는 그것으로 충분하다.

## 1. 먼저 검토한 반례

### 1.1 사망 좌표는 원인이 아니라 결과다

중립이 없는 조작에서 아바타는 언제나 오르거나 내린다. 회랑 밖으로 나간 시점과
벽에 닿는 시점 사이에는 언제나 거리가 있고, 좁은 통로일수록 짧고 넓은 통로일수록
길다. 사망 x 를 그대로 히스토그램으로 쌓으면 **실수가 일어난 자리가 아니라 그
결과가 드러난 자리**가 집계되고, 좁은 섹터가 앞 섹터의 죄를 뒤집어쓴다.

솔버는 이 문제를 풀 수 있다. `S[k] = F[k] ∩ B[k]` 를 이미 계산하므로, 사망
좌표 하나만 있어도 **이탈 지점의 상계**를 구할 수 있다.

```
R[k] : 사망 지점 {y_d} 에서 시작해 자유 구간 안에서 뒤로 팽창시킨 집합
       (전진과 같은 dilate 를 반대 방향으로 쓴다. S 가 아니라 free 로만 자른다)
k*   = max { k ≤ k_d : R[k] ∩ S[k] ≠ ∅ }
```

`k*` 이후로는, 이 사망에 도달하는 어떤 입력열이든 이미 생존 회랑 밖이었다는 뜻이다.
즉 **실수는 `x_{k*}` 이전에 일어났다.** 궤적을 저장하지 않고도 구해지므로
클라이언트 페이로드가 커지지 않는다. 집계는 `x_d` 가 아니라 `x_{k*}` 에 한다.

정직하게 말하면 `k*` 는 상계다 — 실제 이탈은 더 이를 수 있다. 그래서 §6 의
궤적 표본 10% 가 필요하다. 그 표본으로 `k*` 와 실제 이탈의 거리를 재고, 거리가
작으면 이후로는 표본을 줄여도 된다.

### 1.2 같은 `1:2` 가 언제나 같은 코스인 것은 이 빌드 안에서만 참이다

0.5.5 에서 `stage-seeds.json` 의 12개 시드가 전부 갈렸다. 0.5.4 에서 수집한
"스테이지 1-2 의 3번 섹터 사망률"은 0.5.5 에서는 다른 코스의 숫자다. 버전 키가
없으면 데이터셋은 **조용히** 오염된다 — 어긋난 티가 나지 않는다는 것이 최악이다.

그래서 모든 이벤트는 **코스 지문**을 달고, 지문이 다른 데이터는 절대 합산하지
않는다. 지문은 난이도를 결정하는 모든 입력의 내용 해시로 런타임에 계산한다.

```
fp = FNV1a-32( JSON.stringify({
       sectors: SECTORS,                       // 수제 18개의 노드 좌표 전부
       seeds:   stage-seeds.json,
       tuning:  BASE_TUNING,
       rates:   도달 가능한 모든 빌드에 대한 resolve() 결과   // ±3 기준 37개
     }) ).toString(16)
```

마지막 항이 중요하다. `axes.ts` 의 눈금-계수 사상은 코드라서 JSON 해시로는
잡히지 않는데, 도달 가능한 빌드 전부의 `(riseRate, fallRate, speed)` 를 넣으면
그 사상이 바뀌는 순간 지문이 바뀐다. 손으로 올리는 버전 상수가 필요 없고,
따라서 **올리는 것을 잊을 수 없다.** 계산은 첫 전송 직전에 한 번만 하고 캐시한다.

### 1.3 서버가 정말 필요한가

지금 필요한 표본은 brief 의 중단 판정이 말하는 **3명**이다. 3명이면 `exportMeta`
와 같은 복사-붙여넣기로 충분하고, 인프라도 개인정보 처리도 남용 방어도 없다.
레포에는 아직 네트워크 호출이 한 줄도 없으며, 이 기능은 **모노레포 최초의
백엔드**가 된다 — 벤더 계정, 비밀키, 운영 비용, 그리고 "런처가 이제 상태를 가진다"가
따라온다.

그럼에도 서버를 권하는 이유는 하나다. 붙여넣기를 요구하는 순간 **가장 중요한
데이터가 빠진다** — 지시 없이 5회 안에 그만둔 사람은 로그도 보내지 않는다.
이탈률을 재려면 이탈한 사람의 데이터가 와야 하고, 그건 자동 전송이어야만 온다.

## 2. 무엇을 기록하는가 — 사망만으로는 분모가 없다

Stage 는 0.5초 뒤 스스로 재시작한다. 1번 섹터에서 계속 죽는 사람은 2~5번 섹터의
사망을 **한 건도** 만들지 않는다. 사망 건수만 세면 언제나 앞 섹터가 가장 어렵게
나온다. 필요한 것은 조건부 사망률이고, 분모는 **그 섹터에 진입한 횟수**다.

진입 횟수는 따로 보낼 필요가 없다. 사망 이벤트에 조각 인덱스가 있으면 "0번부터
그 조각까지 진입했다"가 유도되고, 클리어 이벤트가 있으면 전 구간 진입이 유도된다.
그러므로 기록 단위는 사망이 아니라 **런의 결말** 세 가지다.

| 종류 | 언제 | 왜 필요한가 |
|---|---|---|
| `death` | 충돌 (Stage 포함 — 지금은 Endless 만 셸로 올라온다) | 분자 |
| `clear` | 종료선 통과 | 분모. 없으면 사망률이 과대추정된다 |
| `abort` | 주행 중 홈으로 나감 / 탭 종료 (`visibilitychange` + `pagehide`) | 이탈률. 중단 판정의 직접 지표 |

`abort` 가 셋 중 가장 값지다. brief 의 중단 판정("지시 없이 5회 이상 재시도")은
지금 미수행이고, 세션당 시도 횟수와 몇 번째 시도에서 떠났는지가 곧 그 판정이다.

## 3. 이벤트 스키마

키를 짧게 쓴다. 한 건 200바이트 안쪽, 배치 50건이 10KB 수준이라 `sendBeacon`
한도(64KB)에 여유 있게 들어간다.

```ts
interface RunEvent {
  k: "death" | "clear" | "abort";
  ts: number;          // Date.now()

  // ── 신원 (익명) ─────────────────────────────
  iid: string;         // 설치 id. UUID v4, localStorage 영속
  sid: string;         // 세션 id. 탭을 열 때 1회 생성, 저장하지 않음

  // ── 코스 지목 ───────────────────────────────
  mode: "stage" | "endless";
  tier?: number;       // stage
  no?: number;         // stage
  seed?: number;       // endless. 재시도로 굴러간 현재 값
  att: number;         // 이 코스에서 몇 번째 시도인가 (state.attempts)

  // ── 재구성 입력 ─────────────────────────────
  cap: 2 | 3;          // axisCap. 게이트 제안이 여기에 달려 있다
  pre: string;         // 출발 프리셋 id
  lanes: string;       // 지나온 게이트 선택. "tbbt" 처럼 t/b 한 글자씩
  bld: [number, number, number];   // 사망 시점 slope/speed/bias. 재구성 대조용

  // ── 사망 지점 (k === "death") ───────────────
  pi: number;          // 조각 인덱스. 분모 유도의 핵심
  pid: string;         // "corridor-down-2" | "gate" | "gen:12" (endless 생성물)
  x: number;           // 월드 x, 소수 1자리
  lx: number;          // 조각 내 지역 x, 소수 1자리
  y: number;           // 소수 1자리
  t: number;           // elapsed sec, 소수 2자리
  hold: 0 | 1;         // 사망 순간 입력 상태
  gw: number;          // deathGap 총 폭. 0 이면 그 순간 그 x 는 완전 폐쇄
  gd: number;          // y 에서 가장 가까운 자유 구간까지의 거리
  sq?: number;         // endless squeeze
  tail?: number[];     // 표본 10% 에만. 직전 1.5초를 60ms 간격으로 [x,y] 25쌍

  // ── 결말 (k !== "death") ────────────────────
  dist?: number;       // endless 도달 거리
  sec?: number;        // 소요 초

  // ── 품질 플래그 ─────────────────────────────
  fps: number;         // 직전 400ms 평균 (onSample 이 이미 준다)
  prac: 0 | 1;         // 연습 모드
  dev: 0 | 1;          // 튜닝 패널 override 가 걸린 런
  hud: 0 | 1;          // 주행 표시 켬/끔
  mob: 0 | 1;          // 포인터 입력 위주인가
}
```

`gd` 가 값싼 요령이다. `state.deathGap` 이 이미 그 x 의 자유 구간(반지름 보정된
중심 좌표)을 들고 있으므로, 거기까지의 거리를 빼는 것은 공짜다. **`gd` 가 작으면
아깝게 빗나간 것이고 크면 애초에 틀린 자리에 있었던 것** — 솔버 재구성 없이도
읽히고, 재구성이 불가능한 Endless 생성 섹터에서도 읽힌다.

`lanes` 는 재구성의 전부다. 게이트 제안은 `(게이트 시드, 통과 시점의 빌드)` 의
결정적 함수이고 빌드는 선택열로 결정되므로, `lanes` 만 있으면 오프라인에서
`buildStageCourse` + `solveCourse` 가 **그 사람이 실제로 탄 코스**를 정확히 재현한다.
`bld` 를 함께 보내는 것은 재구성 결과와 대조해 불일치를 잡기 위한 감시 장치다 —
불일치가 나오면 지문 관리나 lane 기록에 버그가 있다는 뜻이다.

### 3.1 Endless 는 부분적으로만 재구성된다

`decisions.md` 에 적힌 대로, 자리 3번부터는 공장이 제때 끝냈는지가 통로 좌표를
가른다. 예산을 지키는 한 실측상 일치하지만 **원리적으로 보장되지 않는다.**
그러므로 Endless 사망은 두 등급으로 나눠 다룬다.

- 자리 0~2 (항상 수제 섹터): Stage 와 같게 완전 재구성.
- 자리 3 이상: 재구성하지 않는다. 유형·목표 난이도·`squeeze`·`gd` 로만 집계한다.

Endless 에 대해 묻고 싶은 것은 "어느 난이도·어느 조임에서 사람이 멈추는가"이지
"어느 픽셀에서 죽었는가"가 아니므로, 이 정도로 충분하다.

## 4. 기록하지 않는 것과 그 이유

- **입력 타임라인.** 물리는 고정 스텝이지만 프레임 나머지가 `dt` 에 의존하므로
  같은 입력열이 같은 궤적을 주지 않는다. 재생이 되지 않는 데이터를 저장하는 것은
  용량만 쓰고 잘못된 확신을 준다.
- **전체 궤적.** `k*` 재구성이 대신한다. 10% 표본만 `tail` 로 받아 그 재구성이
  맞는지 검산한다.
- **IP·UA 원문·화면 해상도 세부.** 지문 재식별의 재료다. 파생 플래그 `mob` 하나만
  둔다. (Vercel 자체 액세스 로그는 이 기능과 별개이며 우리가 읽지 않는다.)
- **입력 키·마우스 좌표·타이밍 원시값.** 게임 밖 정보가 섞일 여지가 있다.

## 5. 데이터 품질 함정

이 목록이 기능의 성패를 가른다. 하나라도 빠지면 그럴듯하지만 틀린 표가 나온다.

1. **재시도 편향** — §2. 분모를 진입 횟수로. `clear` 이벤트 필수.
2. **연습 모드** — 체크포인트가 있으면 난이도가 다른 게임이다. `prac` 로 분리.
   기록에 안 넣는 것과 같은 이유로 집계에서도 뺀다.
3. **튜닝 패널** — `T` 로 물리를 바꾼 런은 다른 게임이다. `dev` 로 분리.
4. **자동 플레이테스트** — puppeteer 시나리오가 실제 엔진에서 실제로 죽는다.
   차단하지 않으면 오토파일럿의 사망이 사람의 사망으로 집계된다. URL 파라미터
   `?telemetry=off` 를 두고 `scripts/playtest/` 가 항상 붙이도록 한다. 기본 차단이
   아니라 **명시 차단**이어야 한다 — 기본 차단으로 두면 사람 데이터도 같이 막힌다.
5. **프레임 저하** — 물리는 하위 스텝으로 쪼개져 관통은 없지만, **입력은 프레임에
   한 번 읽힌다.** 30fps 면 입력 격자가 33ms 이고 티어 4 의 여유는 118ms 다.
   무시할 수 없는 크기이므로 `fps < 50` 사망은 별도 집계하고 난이도 판정에서 뺀다.
6. **지문 불일치** — §1.2. 합산 금지. 분석기가 섞인 입력을 받으면 거부한다.
7. **한 사람이 데이터의 대부분을 만든다** — 제작자가 가장 많이 플레이한다.
   `iid` 당 이벤트 상한을 두거나 `iid` 별로 정규화한 뒤 합산한다. 제작자 `iid` 는
   분석기에서 제외 목록으로 뺀다.

## 6. 전송 — 마찰 0의 재시도를 깨지 않는 것

brief 의 불변 조항은 "사망에서 다음 시도까지 0.5초"다. 전송이 그 경로에 끼면 안 된다.

- 사망 콜백은 **큐에 push 만** 한다. `await` 도 `fetch` 도 프레임 루프에서 하지 않는다.
- 배치 조건: 50건이 찼거나, 15초가 지났거나, `visibilitychange`(hidden) 또는
  `pagehide` 가 왔을 때.
- 전송은 `navigator.sendBeacon`. 탭을 닫아도 살아남는다 — `abort` 이벤트를 받으려면
  이것이어야 한다. 미지원 환경은 `fetch(..., { keepalive: true })` 로 떨어진다.
- 실패하면 `localStorage["wave-runner/tele/q/v1"]` 에 쌓고 다음 실행에 먼저 보낸다.
  상한 500건, 초과 시 **오래된 것부터** 버린다. 최신이 더 가치 있다.
- 응답 처리: 4xx 면 재시도해도 소용없으니 큐에서 버린다. 5xx·네트워크 오류면 유지한다.

## 7. 서버

### 7.1 어디에 두는가

배포되는 것은 런처(Next 15, Vercel) 하나뿐이고, 게임은 `/runs/wave-runner/index.html`
의 iframe 이다 — **프로덕션에서 동일 출처**라 상대 경로 `/api/...` 로 CORS 없이
닿는다. 개발에서는 vite(5173)와 next(3000)가 다른 출처이므로 `vite.config.ts` 에
`/api` 프록시를 둔다.

엔드포인트는 wave-runner 전용이 아니라 레포 공용으로 만든다. 다른 프로토타입도
같은 질문을 하게 된다.

```
POST /api/telemetry/[project]
Content-Type: application/json

{ v: 1, fp: "8f3a91c2", iid, sid, events: RunEvent[] }   // 최대 50건 / 32KB

204 No Content        // 본문 없음. 클라이언트가 응답에서 얻을 것이 없다
400 스키마 위반 · 413 초과 · 429 레이트 · 503 스토어 장애
```

### 7.2 스토어

서버리스 파일시스템은 휘발이므로 외부 저장이 필요하다. **Upstash Redis(Vercel
Marketplace)의 리스트를 권한다.**

```
RPUSH  wave:ev:<fp>  <직렬화된 배치>
LTRIM  wave:ev:<fp>  -50000 -1
```

append 만 하면 되고 조회는 오프라인이므로 질의 능력이 필요 없다. 배치 하나가
명령 하나라 무료 한도(일 1만 명령) 안에서 하루 50만 이벤트까지 들어간다.
Postgres 는 스키마와 마이그레이션이 따라오고, Blob 은 append 가 없어 작은 객체가
수천 개 생긴다 — 둘 다 이 규모에 과하거나 안 맞는다.

덤프는 dev 전용 스크립트가 `LRANGE` 로 전량을 끌어 NDJSON 으로 떨어뜨린다.
읽기 토큰은 로컬 `.env` 에만 두고 런처에는 쓰기 토큰만 준다.

### 7.3 남용 방어

인증 없는 공개 POST 다. 최소한 이 다섯 개.

1. 배치 50건·32KB 상한, 초과 413.
2. 스키마 엄격 검증. 모르는 키는 버리고, 타입이 어긋나면 400.
3. 레이트: `iid` 분당 30요청, IP 분당 120. Redis `INCR` + `EX 60`.
4. `LTRIM` 으로 저장 상한을 강제해 비용이 발산하지 않게 한다.
5. **이 데이터는 조작 가능하다. 기록·리더보드·해금에 절대 쓰지 않는다.**
   용도는 관측 하나뿐이고, 그래서 위조가 비용은 늘려도 게임을 망치지는 못한다.

## 8. 개인정보

brief 는 "설치도 **계정도** 튜토리얼도 없다"고 못박았다. 그 조항을 지킨다.

- 식별자는 익명 설치 id(UUID v4) 하나. 이메일·이름·로그인 없음.
- 페이로드에 개인정보가 없다. 좌표·시각·빌드 눈금뿐이다.
- 첫 실행에 한 줄 고지와 **끄기**. 끄면 즉시 전송을 멈추고 큐를 비운다.
  설정은 `meta.hud` 옆에 `meta.telemetry` 로 둔다.
- 기본값은 **켬**을 권한다. 수집 대상이 게임 플레이 좌표뿐이고, 끄기가 한 번의
  클릭이며, 프로토타입 단계에서 표본이 0 이면 기능 자체가 무의미해지기 때문이다.
  다만 이건 판단이므로 뒤집을 수 있다 — 끔이 기본이면 §1.3 의 이탈률은 사실상
  못 잰다는 것이 대가다.

## 9. 해석 — 실제 산출물

`projects/wave-runner/tools/death-report/` (분석기는 검증이 아니므로 `tests/verify/`
가 아니다). 입력은 NDJSON 덤프, 출력은 표 넷과 그림 하나.

**표 A — 섹터별 조건부 사망률**

| 섹터 id | 진입 | 사망 | 사망률 | 솔버 최소 여유 | `k*` 중앙값 위치 |
|---|---|---|---|---|---|

**표 B — 여유 구간별 사망률.** 여유 20ms 밴드마다 사망률을 낸다. 지금 티어 목표치
(200/180/150/130ms)는 프로브 추정에서 나온 값이고 사람으로 검증된 적이 없다.
이 표가 **목표치를 데이터로 다시 정하는 근거**이며, 이 기능의 가장 큰 수확이다.

**표 C — lane 경로별 사망률.** 큐레이션이 "모든 경로 통과 가능"을 이미 보장하므로,
여기서 찾는 것은 *이론상 가능하지만 사람이 못 하는* 경로다. 0.5.1 에서 없앤
"함정 경로"의 사람 버전이다.

**표 D — 시도 분포.** 세션당 시도 횟수, 첫 클리어까지의 중앙 시도 횟수,
`abort` 이전 시도 횟수 분포. brief 의 중단 판정이 여기서 읽힌다.

**그림 — 코스 지도 위의 사망 히스토그램.** `tests/verify/course-map/` 파이프라인이
이미 생존 회랑을 그리고 있으므로, 그 위에 `k*` 밀도를 겹치면 끝이다.
**솔버가 예측한 최난 구간과 사람이 실제로 죽는 구간이 겹치는지**가 한 장에서 읽힌다.

### 9.1 판정 규칙 (초안)

- **표본 바닥**: 섹터당 사망 30건, 스테이지당 완주 시도 20건 미만이면 판정 보류.
  3명으로는 섹터별 판정이 서지 않는다는 것을 숫자로 못박아 둔다.
- 한 섹터가 그 티어 사망의 40% 이상 → 재큐레이션 대상.
- 여유가 더 큰 밴드의 사망률이 더 작은 밴드보다 높다 → **솔버가 못 보는 요인**이
  있다(시각적 오독, 리듬, 게이트 직후의 인지 부하). 섹터 도형을 의심할 자리다.
- 첫 클리어까지의 중앙 시도 횟수가 티어 순서와 어긋난다 → 티어 곡선이 수치상
  단조여도 실제로는 뒤집혀 있다.
- `gd` 중앙값이 큰 섹터 → 미세 조작 실패가 아니라 **경로 판단 실패**다. 폭을
  넓히는 것이 아니라 선행 가시성이나 형상 가독성을 봐야 한다.

### 9.2 분석기 자체의 검증

- 재구성한 빌드와 이벤트의 `bld` 가 일치하는가. 불일치율이 0 이 아니면 즉시 조사.
- 이벤트의 `gw`·`gd` 가 재구성한 자유 구간에서 다시 계산한 값과 일치하는가.
- `tail` 표본에서, 궤적이 실제로 `S` 를 벗어난 지점과 `k*` 의 거리 분포.
  이 거리가 작아야 §1.1 의 상계가 쓸모 있다.

4. `spec.md` 의 3단계 비목표에 "계정 동기화·리더보드"가 있다. 이 기능은 둘 다
   아니지만 레포 최초의 백엔드라는 점에서 같은 문턱을 넘는다 — 비목표 항목을
   갱신할지 결정이 필요하다.
