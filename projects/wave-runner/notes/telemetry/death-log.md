# 설계 — 사망 기록 수집과 밸런스 조정 (Vercel 기준)

> **상태: 1차(0.5.6) · 2차(0.5.7) 구현 완료.** 수집 · 엔드포인트 · Blob · 확인 경로 ·
> 분석기(표 A~D + 그림)까지 섰다. 구현하며 설계에서 달라진 것은 각 절에 표시해 두었다.
>
> **가장 큰 정정은 §1.1 이다** — 이 문서 전체의 출발점이었던 "사망 좌표는 원인보다 한참
> 하류다"가 크기를 재 보니 성립하지 않았다.

> 요청: "사용자 플레이 중 죽은 위치를 서버에 기록했다가 나중에 개발자가 확인하고
> 밸런스를 조정할 때 활용." 추가 조건: **어떤 식으로든 수집되고 확인할 수만 있으면 된다.**
> 이 문서는 그 요청을 Vercel 위에서 구현 가능한 수준으로 구체화한 것이다. 코드는 아직 없다.

## 결론

**Vercel Blob(비공개 스토어) + 런처의 라우트 핸들러 하나.** 외부 벤더 계정이 없고,
확인은 CLI 두 줄이며, 레포에 새로 생기는 런타임 비밀키가 없다(OIDC).

```
게임(iframe) ──POST──▶ launcher /api/telemetry/[project] ──put()──▶ Vercel Blob (private)
                                                                        │
개발자 ◀── vercel blob list / get ──────────────────────────────────────┘
        └─▶ tools/death-report — 솔버로 코스를 재구성해 표와 그림을 만든다
```

다만 **"죽은 위치"를 그대로 저장하면 틀린 곳을 고치게 된다.** 이 프로젝트는 난이도를
이미 수치로 안다 — 솔버가 재는 생존 회랑 여유(ms)다. 사망 기록이 새로 주는 것은
난이도가 아니라 **그 수치가 사람 체감과 어디서 어긋나는가**이고, 그 어긋남만이 지금
측정 불가능한 값이다. 그래서 §1~§3(무엇을 어떤 모양으로 담는가)이 §4(어디에 넣는가)보다
길다. 배관은 하루면 되고, 스키마가 틀리면 모은 데이터를 버린다.

## 1. 설계 전제

### 1.1 사망 좌표는 원인이 아니라 결과다

중립이 없는 조작에서 아바타는 언제나 오르거나 내린다. 생존 회랑을 벗어난 시점과
벽에 닿는 시점 사이에는 언제나 거리가 있고, 좁은 통로일수록 짧고 넓은 통로일수록
길다. 사망 x 를 그대로 히스토그램으로 쌓으면 **실수가 일어난 자리가 아니라 그
결과가 드러난 자리**가 집계되고, 좁은 섹터가 앞 섹터의 죄를 뒤집어쓴다.

솔버가 이 문제를 푼다. `S[k] = F[k] ∩ B[k]` 를 이미 계산하므로, 사망 좌표 하나만
있어도 **이탈 지점의 상계**가 구해진다.

```
R[k] : 사망 지점 {y_d} 에서 시작해 자유 구간 안에서 뒤로 팽창시킨 집합
       (전진과 같은 dilate 를 반대 방향으로. S 가 아니라 free 로만 자른다)
k*   = max { k ≤ k_d : R[k] ∩ S[k] ≠ ∅ }
```

`k*` 이후로는, 이 사망에 도달하는 어떤 입력열이든 이미 회랑 밖이었다는 뜻이다.
즉 **실수는 `x_{k*}` 이전에 일어났다.** 궤적을 저장하지 않고도 구해지므로 페이로드가
커지지 않는다. 집계는 `x_d` 가 아니라 `x_{k*}` 에 한다.

정직하게 말하면 `k*` 는 상계다 — 실제 이탈은 더 이를 수 있다.

### 1.1a 측정 결과 — 전제가 틀렸다 (2차, 0.5.7)

분석기를 만들어 실제로 재 보니 **`k*` 가 사망 x 에서 중앙 1.1 · 최대 5.2 월드 단위**
앞에 붙는다. 섹터 하나가 460 단위다. 조각을 옮긴 사망은 0% 였다.

이유는 지오메트리에 있다. 생존 회랑을 죄는 쪽 경계가 **곧 플레이어가 부딪히는 벽**이다 —
가파른 램프에서 뒤처진 기체는 그 램프의 벽에 긁히고, 회랑은 바로 그 벽에 눌려 있다.
그래서 회랑을 벗어나는 자리와 벽에 닿는 자리가 사실상 같은 x 다.

결과가 둘이다.

- **사망 x 로 집계해도 섹터 단위에서는 틀리지 않는다.** 이 문서가 처음에 건 걱정
  ("좁은 섹터가 앞 섹터의 죄를 뒤집어쓴다")은 크기가 작아 실무적으로 성립하지 않았다.
- **`k*` 는 상계로서 물리지 않는다.** "실수는 여기보다 늦지 않다"고 말하지만 그 자리가
  사망 지점이라 아무것도 배제하지 못한다. 실제 이탈 지점을 알려면 궤적이 필요하고,
  그것이 §3.1 의 `tail` 이다 — **선택 항목에서 필수로 승격됐다.**

`k*` 계산은 그대로 둔다. 값이 싸고(조각별 추적을 한 번 더 훑을 뿐), 조각을 옮기는
사망이 생기면 그때 잡아 주며, 회랑이 자유 구간보다 훨씬 좁아지는 코스가 들어오면
다시 물리기 시작한다.

### 1.2 같은 `1:2` 가 언제나 같은 코스인 것은 이 빌드 안에서만 참이다

0.5.5 에서 `stage-seeds.json` 의 12개 시드가 전부 갈렸다. 0.5.4 에서 모은 "스테이지
1-2 의 3번 섹터 사망률"은 0.5.5 에서는 다른 코스의 숫자다. 버전 키가 없으면
데이터셋은 **조용히** 오염된다 — 어긋난 티가 나지 않는 것이 최악이다.

모든 이벤트는 **코스 지문**을 달고, 지문이 다른 데이터는 절대 합산하지 않는다.
지문은 난이도를 결정하는 모든 입력의 내용 해시로 런타임에 계산한다.

```
fp = FNV1a-32( JSON.stringify({
       sectors: SECTORS,                     // 수제 18개의 노드 좌표 전부
       seeds:   stage-seeds.json,
       tuning:  BASE_TUNING,
       rates:   도달 가능한 모든 빌드의 resolve() 결과   // ±3 기준 37개
     }) ).toString(16)
```

마지막 항이 중요하다. `axes.ts` 의 눈금-계수 사상은 코드라서 JSON 해시로는 잡히지
않는데, 도달 가능한 빌드 전부의 `(riseRate, fallRate, speed)` 를 넣으면 그 사상이
바뀌는 순간 지문이 바뀐다. **손으로 올리는 버전 상수가 없으므로 올리는 것을 잊을 수
없다.** 계산은 첫 전송 직전 한 번만 하고 캐시한다.

지문은 저장 경로에도 들어간다(§4.2). 섞일 수 없는 것을 디렉터리로 분리해 두면
분석기가 실수로 합산할 길이 막힌다.

## 2. 기록 단위 — 사망만으로는 분모가 없다

Stage 는 0.5초 뒤 스스로 재시작한다. 1번 섹터에서 계속 죽는 사람은 2~5번 섹터의
사망을 **한 건도** 만들지 않는다. 사망 건수만 세면 언제나 앞 섹터가 가장 어렵게
나온다. 필요한 것은 조건부 사망률이고, 분모는 **그 섹터에 진입한 횟수**다.

진입 횟수는 따로 보낼 필요가 없다. 사망 이벤트에 조각 인덱스가 있으면 "0번부터 그
조각까지 진입했다"가 유도되고, 클리어 이벤트가 있으면 전 구간 진입이 유도된다.
그러므로 기록 단위는 사망이 아니라 **런의 결말** 셋이다.

| 종류 | 언제 | 왜 필요한가 |
|---|---|---|
| `death` | 충돌. **Stage 포함** — 지금은 Endless 만 셸로 올라온다 | 분자 |
| `clear` | 종료선 통과 | 분모. 없으면 사망률이 과대추정된다 |
| `abort` | 주행 중 홈으로 나감 / 탭 종료(`visibilitychange`·`pagehide`) | 이탈률 |

`abort` 가 셋 중 가장 값지다. brief 의 중단 판정("지시 없이 5회 이상 재시도")은 지금
미수행이고, 세션당 시도 횟수와 몇 번째 시도에서 떠났는지가 곧 그 판정이다.
그리고 이것이 **서버를 세우는 이유**이기도 하다 — 붙여넣기식 수집으로는 그만두고
떠난 사람의 데이터가 영원히 오지 않는다.

## 3. 이벤트 스키마

키를 짧게 쓴다. 한 건 200바이트 안쪽, 배치 50건이 10KB 수준이라 `sendBeacon`
한도(64KB)에 여유 있게 들어간다.

```ts
interface RunEvent {
  k: "death" | "clear" | "abort";
  ts: number;          // Date.now()

  // 신원(iid·sid)과 지문(fp)은 **봉투에** 한 번만 싣는다 — 배치 안에서 언제나 같은
  // 값이라 이벤트마다 반복하면 페이로드의 절반이 된다. 서버가 저장하면서 각 줄에
  // 다시 찍으므로, 파일의 한 줄은 그 자체로 완결된다(`cat *.ndjson | jq` 가 그대로 된다).

  // ── 코스 지목 ───────────────────────────────
  mode: "stage" | "endless";
  tier?: number;       // stage
  no?: number;         // stage
  seed?: number;       // endless. 재시도로 굴러간 현재 값
  att: number;         // 이 코스에서 몇 번째 시도인가 (state.attempts)

  // ── 재구성 입력 ─────────────────────────────
  cap: 2 | 3;          // axisCap. 게이트 제안이 여기에 달려 있다
  pre: string;         // 출발 프리셋 id
  // 지나온 게이트 선택. "tbbt" 처럼 t/b 한 글자씩.
  // **빈 문자열이 정상이다** — 첫 게이트 전에 죽은 런이고, 그것이 신규 플레이어의
  // 가장 흔한 사망이다. 구현에서 서버가 이것을 400 으로 거부하는 버그를 냈다.
  lanes: string;
  bld: [number, number, number];   // 사망 시점 slope/speed/bias. 재구성 대조용

  // ── 사망 지점 (k === "death") ───────────────
  pi: number;          // 조각 인덱스. 분모 유도의 핵심
  pid: string;         // "corridor-down-2" | "gate" | "gen:12" (endless 생성물)
  x: number;           // 월드 x, 소수 1자리
  lx: number;          // 조각 내 지역 x, 소수 1자리
  y: number;           // 소수 1자리
  t: number;           // elapsed sec, 소수 2자리
  hold: 0 | 1;         // 사망 순간 입력 상태
  gw: number;          // deathGap 총 폭. 0 이면 그 순간 그 x 는 완전 폐쇄
  gd: number;          // y 에서 가장 가까운 자유 구간까지의 거리

  // ── 결말 (k !== "death") ────────────────────
  dist?: number;       // endless 도달 거리
  sec?: number;        // 소요 초

  // ── 품질 플래그 ─────────────────────────────
  fps: number;         // 직전 400ms 평균 (onSample 이 이미 준다)
  prac: 0 | 1;         // 연습 모드
  dev: 0 | 1;          // 튜닝 패널 override 가 걸린 런
  hud: 0 | 1;          // 주행 표시 켬/끔
  mob: 0 | 1;          // 포인터 입력 위주인가
}
```

`gd` 가 값싼 요령이다. `state.deathGap` 이 이미 그 x 의 자유 구간(반지름 보정된 중심
좌표)을 들고 있으므로 거기까지의 거리를 빼는 것은 공짜다. **`gd` 가 작으면 아깝게
빗나간 것이고 크면 애초에 틀린 자리에 있었던 것** — 솔버 재구성 없이도 읽히고,
재구성이 불가능한 Endless 생성 섹터에서도 읽힌다.

`lanes` 는 재구성의 전부다. 게이트 제안은 `(게이트 시드, 통과 시점의 빌드)` 의
결정적 함수이고 빌드는 선택열로 결정되므로, `lanes` 만 있으면 오프라인에서
`buildStageCourse` + `solveCourse` 가 **그 사람이 실제로 탄 코스**를 정확히 재현한다.
`bld` 를 함께 보내는 것은 재구성 결과와 대조해 불일치를 잡는 감시 장치다 — 불일치가
나오면 지문 관리나 lane 기록에 버그가 있다는 뜻이다.

**Endless 는 부분적으로만 재구성된다.** `decisions.md` 대로 자리 3번부터는 공장이
제때 끝냈는지가 통로 좌표를 가르고, 예산을 지키는 한 실측상 일치하지만 원리적으로
보장되지 않는다. 그래서 자리 0~2 는 Stage 와 같게 완전 재구성하고, 자리 3 이상은
재구성하지 않고 유형·목표 난이도·`squeeze`·`gd` 로만 집계한다. Endless 에 묻고 싶은
것은 "어느 난이도·어느 조임에서 멈추는가"이지 "어느 픽셀에서 죽었는가"가 아니다.

### 3.1 기록하지 않는 것

- **입력 타임라인.** 물리는 고정 스텝이지만 프레임 나머지가 `dt` 에 의존하므로 같은
  입력열이 같은 궤적을 주지 않는다. 재생되지 않는 데이터는 용량만 쓰고 잘못된 확신을 준다.
- **전체 궤적.** ~~`k*` 재구성이 대신한다.~~ **정정(§1.1a)**: `k*` 가 상계로서 물리지
  않으므로 궤적 없이는 상류 원인을 못 짚는다. 전량은 여전히 과하고, `tail`(직전 1.5초를
  60ms 간격으로 25점) 10% 표본이 필요하다.
- **IP·UA 원문·화면 해상도 세부.** 지문 재식별의 재료다. 파생 플래그 `mob` 하나만 둔다.

## 4. Vercel 구성

### 4.1 왜 Blob 인가

셋을 놓고 골랐다.

| 선택지 | 판정 |
|---|---|
| **런타임 로그에 `console.log`** | 탈락. Hobby 는 런타임 로그를 **1시간**만 보관하고 Log Drains 는 Pro 이상이다. "나중에 확인"이 성립하지 않는다 |
| **Redis(Upstash)** | 가능하지만 Vercel KV 는 사문화되어 Marketplace 통합, 즉 **외부 벤더 계정과 토큰**이 새로 생긴다 |
| **Vercel Blob (비공개)** | 채택. 1st-party, Hobby 무료 한도 안, CLI 로 바로 열람, 연결된 프로젝트에서는 OIDC 로 인증해 토큰을 레포에 두지 않아도 된다 |

Blob 은 append 가 없어 **배치 하나가 객체 하나**가 된다. 앞선 검토에서는 이 점 때문에
Blob 을 뺐지만, 배치를 50건으로 묶으면 테스터 한 세션이 객체 열 개 남짓이고 3명 ×
20세션이면 600개다 — 한 번의 `list`(1000개 단위 페이지네이션) 안에 들어간다.
**규모가 작아서 단점이 단점이 아니다.** 객체가 수천 개로 늘면 하루치를 한 객체로
합치는 압축 단계를 넣거나 Upstash 로 갈아탄다. 그때 바꿔도 클라이언트는 그대로다.

### 4.2 저장 경로

```
tele/<project>/<fp>/<YYYY-MM-DD>/<ts>-<rand>.ndjson
예: tele/wave-runner/8f3a91c2/2026-09-20/1758312001234-k3f9.ndjson
```

- `<fp>` 로 갈라 두면 §1.2 의 "지문이 다른 데이터는 합산 금지"가 **경로 구조로** 강제된다.
- `<YYYY-MM-DD>` 는 기간 덤프를 접두사 하나로 끝내기 위한 것이다.
- 본문은 NDJSON — 한 줄에 이벤트 하나. 객체를 이어 붙이면 그대로 하나의 NDJSON 이 된다.
- `put(..., { access: "private", addRandomSuffix: true, contentType: "application/x-ndjson" })`.
  랜덤 접미사에 맡기면 이름 충돌로 덮어쓸 일이 없다. (`@vercel/blob` 2.8.0 에서
  `access: "private"` 확인됨 — 설계 시점의 열린 질문이었다.)

**구현에서 더한 것 — 개발용 파일 폴백.** `BLOB_READ_WRITE_TOKEN` 이 없고 프로덕션이
아니면 같은 경로 모양으로 `.telemetry/` 에 떨어뜨린다. 두 조건을 모두 요구하므로
배포에서는 절대 파일로 새지 않는다. 이유는 확인 가능성이다 — 스토어를 붙이기 전에는
성공 경로를 한 번도 밟아 볼 수 없고, 그러면 "수집된다"를 배포해 봐야만 알게 된다.

### 4.3 라우트 핸들러

`launcher/app/api/telemetry/[project]/route.ts` — wave-runner 전용이 아니라 레포 공용으로
둔다. 다른 프로토타입도 같은 질문을 하게 된다.

```
POST /api/telemetry/wave-runner
Content-Type: application/json

{ v: 1, fp: "8f3a91c2", iid, sid, events: RunEvent[] }

204 No Content        // 본문 없음. 클라이언트가 응답에서 얻을 것이 없다
400 스키마 위반 · 404 모르는 project · 413 초과 · 429 레이트 · 503 스토어 장애
```

핸들러가 하는 일은 넷뿐이다. 본문 크기 확인 → 스키마 검증 → `project` 화이트리스트
대조 → `put()`. 응답을 기다릴 이유가 없으므로 204 로 끝낸다.

`runtime` 은 Node(기본)로 둔다. `@vercel/blob` 이 Edge 에서도 돌지만 굳이 옮길 이유가 없다.

### 4.4 확인 — CLI 두 줄

이것이 "어떤 식으로든 확인만 되면 된다"에 대한 답이다. 덤프용 라우트도, 대시보드도,
읽기 토큰도 필요 없다. 연결된 프로젝트에서 CLI 가 OIDC 로 인증하므로 비공개
스토어도 그대로 열린다.

```bash
vercel blob list --prefix tele/wave-runner/8f3a91c2/
vercel blob get  tele/wave-runner/8f3a91c2/2026-09-20/1758312001234-k3f9.ndjson
```

`get` 은 기본이 stdout 이므로 여러 객체를 `>>` 로 이어 붙이면 곧바로 분석기 입력이 된다.
**구현에서 바뀐 것 — CLI 가 아니라 SDK 로 읽는다.** 설계는 "CLI 두 줄"을 확인 경로로
잡았지만, 구현하며 두 가지가 걸렸다. 플래그 이름과 표 출력 형식에 기대야 하고, 무엇보다
**객체가 1000개를 넘는 순간 목록 한 번으로는 조용히 잘린다.** 조용히 잘리는 것이 최악이다 —
보고서는 그대로 나오고 숫자만 틀린다. `tools/death-report/pull.ts` 가 커서로 끝까지 돌고,
개발 폴백(`--local`)도 같은 도구가 읽는다. CLI 는 한 번 들여다볼 때 쓰는 보조 수단으로 남는다.

그리고 `doctor.ts` 를 더했다. 쓰기 → 비공개 확인 → 목록 → 읽기 → 삭제를 한 번 돌려
**어디서 끊기는지 이름을 붙인다.** 코드가 있다고 수집이 되는 것이 아니고, 토큰 없음 ·
공개 스토어 · 한도 잠금 · 미연결은 증상이 전부 다르다. 특히 공개/비공개는 코드에서
확인할 길이 없어(스토어를 만들 때 정해진다) 인증 없는 요청을 실제로 한 번 던져 본다.

### 4.5 한도와 잠금 — 가장 중요한 운영 위험

Hobby 의 Blob 무료 한도는 **저장 1GB · 전송 월 10GB** 다. 데이터 자체는 이 근처에도
못 간다(3명 × 20세션이면 6MB 수준). 문제는 한도를 넘겼을 때의 거동이다 —
**한도를 초과하면 스토어 접근이 막히고 30일을 기다려야 한다. 그동안 이미 모은
데이터를 내보내는 것도 막힌다.**

그래서 방어는 위생이 아니라 **이미 모은 데이터를 지키는 일**이다.

1. 본문 32KB · 이벤트 50건 상한. 초과 413.
2. 스키마 엄격 검증. 모르는 키는 버리고 타입이 어긋나면 400. 검증 전에 `put` 하지 않는다.
3. 인스턴스 메모리 레이트 리미터(`iid` 분당 6요청). 서버리스라 인스턴스별이지만,
   막으려는 것은 작정한 공격자가 아니라 **폭주하는 재시도 루프**다.
4. **주 1회 덤프해 레포 밖 로컬에 보관한다.** 스토어가 잠겨도 데이터는 이미 손에 있다.
   이것이 실질적인 방어이고, 나머지 셋은 잠길 확률을 낮출 뿐이다.
5. 이 데이터는 조작 가능하다. **기록·리더보드·해금에 절대 쓰지 않는다.** 용도가
   관측 하나뿐이라 위조가 비용은 늘려도 게임을 망치지는 못한다.

### 4.6 전송과 개발 환경

brief 의 불변 조항은 "사망에서 다음 시도까지 0.5초"다. 전송이 그 경로에 끼면 안 된다.

- 사망 콜백은 **큐에 push 만** 한다. 프레임 루프에서 `await` 도 `fetch` 도 하지 않는다.
- 배치 조건: 50건이 찼거나, 15초가 지났거나, `visibilitychange`(hidden)·`pagehide` 가 왔을 때.
- `navigator.sendBeacon(url, new Blob([json], { type: "application/json" }))`.
  탭을 닫아도 살아남는다 — `abort` 를 받으려면 이것이어야 한다. 미지원 환경은
  `fetch(..., { keepalive: true })` 로 떨어진다.
- 실패하면 `localStorage["wave-runner/tele/q/v1"]` 에 쌓고 다음 실행에 먼저 보낸다.
  상한 500건, 초과 시 **오래된 것부터** 버린다. 최신이 더 가치 있다.
- 4xx 면 재시도해도 소용없으니 큐에서 버린다. 5xx·네트워크 오류면 유지한다.
- **구현에서 더한 것 — 지수 백오프.** 실패가 이어지면 간격을 두 배씩 늘린다(최대 8분).
  이것이 없으면 엔드포인트가 죽어 있을 때 큐가 계속 50 이상이라 **사망마다 재전송을
  때리는 뜨거운 루프**가 된다. 백오프 중에는 크기 조건으로도 보내지 않는다.

**프로덕션은 동일 출처다.** 게임은 `/runs/wave-runner/index.html` 의 iframe 이고
엔드포인트는 같은 도메인의 `/api/...` 이므로 CORS 도 프리플라이트도 없다.
`sendBeacon` 은 프리플라이트를 할 수 없으므로 이 점이 중요하다.

**개발은 다른 출처다.** vite(5173)와 next(3000)가 갈리므로 `app/vite.config.ts` 에
`/api` → `http://127.0.0.1:3000` 프록시를 둔다. 브라우저 입장에서 동일 출처가 되어
프로덕션과 같은 코드가 돈다.

### 4.7 환경 변수

| 이름 | 어디 | 값 |
|---|---|---|
| `BLOB_READ_WRITE_TOKEN` | Vercel 프로젝트에 Blob 스토어를 연결하면 자동 주입 | 레포에 커밋하지 않는다 |
| `TELEMETRY_PROJECTS` | Vercel 프로젝트 환경변수 | `wave-runner` 등 허용 목록. 비어 있으면 엔드포인트가 전부 404 |

CLI 는 연결된 프로젝트에서 OIDC 로 인증하므로 로컬에 읽기 토큰을 따로 두지 않는다.
`vercel link` 만 되어 있으면 된다.

## 5. 데이터 품질 함정

이 목록이 기능의 성패를 가른다. 하나라도 빠지면 그럴듯하지만 틀린 표가 나온다.

1. **재시도 편향** — §2. 분모를 진입 횟수로. `clear` 이벤트 필수.
2. **연습 모드** — 체크포인트가 있으면 난이도가 다른 게임이다. `prac` 로 분리.
   기록에 안 넣는 것과 같은 이유로 집계에서도 뺀다.
3. **튜닝 패널** — `T` 로 물리를 바꾼 런은 다른 게임이다. `dev` 로 분리.
4. **자동 플레이테스트** — puppeteer 시나리오가 실제 엔진에서 실제로 죽는다. 차단하지
   않으면 오토파일럿의 사망이 사람의 사망으로 집계된다. URL 파라미터 `?telemetry=off`
   를 두고 `scripts/playtest/` 가 항상 붙인다. 기본 차단이 아니라 **명시 차단**이어야
   한다 — 기본 차단으로 두면 사람 데이터도 같이 막힌다.
5. **프레임 저하** — 물리는 하위 스텝으로 쪼개져 관통은 없지만, **입력은 프레임에 한 번
   읽힌다.** 30fps 면 입력 격자가 33ms 이고 티어 4 의 여유는 118ms 다. 무시할 수 없는
   크기이므로 `fps < 50` 사망은 별도 집계하고 난이도 판정에서 뺀다.
6. **지문 불일치** — §1.2. 경로가 갈라 두지만, 분석기도 섞인 입력을 받으면 거부한다.
7. **한 사람이 데이터의 대부분을 만든다** — 제작자가 가장 많이 플레이한다. `iid` 별로
   정규화한 뒤 합산하고, 제작자 `iid` 는 제외 목록으로 뺀다.

## 6. 개인정보

brief 는 "설치도 **계정도** 튜토리얼도 없다"고 못박았다. 그 조항을 지킨다.

- 식별자는 익명 설치 id(UUID v4) 하나. 이메일·이름·로그인 없음.
- 페이로드에 개인정보가 없다. 좌표·시각·빌드 눈금뿐이다.
- 스토어는 **비공개**로 만든다. 공개 스토어는 URL 만 알면 누구나 읽는다.
- 첫 실행에 한 줄 고지와 **끄기**. 끄면 즉시 전송을 멈추고 큐를 비운다. 설정은
  `meta.hud` 옆에 `meta.telemetry` 로 둔다.
- 기본값은 **켬**을 권한다. 수집 대상이 게임 플레이 좌표뿐이고, 끄기가 한 번의
  클릭이며, 표본이 0 이면 기능 자체가 무의미해지기 때문이다. 판단이므로 뒤집을 수
  있고, 끔이 기본이면 §2 의 이탈률은 사실상 못 잰다는 것이 대가다.

## 7. 해석 — 실제 산출물

`projects/wave-runner/tools/death-report/` (분석기는 검증이 아니므로 `tests/verify/` 가
아니다). 입력은 §4.4 로 받은 NDJSON, 출력은 표 넷과 그림 하나.

**표 A — 섹터별 조건부 사망률**

| 섹터 id | 진입 | 사망 | 사망률 | 솔버 최소 여유 | `k*` 중앙값 위치 |
|---|---|---|---|---|---|

**표 B — 여유 구간별 사망률.** 여유 20ms 밴드마다 사망률을 낸다. 지금 티어 목표치
(200/180/150/130ms)는 프로브 추정에서 나온 값이고 사람으로 검증된 적이 없다. 이 표가
**목표치를 데이터로 다시 정하는 근거**이며, 이 기능이 존재하는 이유다.

**표 C — lane 경로별 사망률.** 큐레이션이 "모든 경로 통과 가능"을 이미 보장하므로,
여기서 찾는 것은 *이론상 가능하지만 사람이 못 하는* 경로다. 0.5.1 에서 없앤 "함정
경로"의 사람 버전이다.

**표 D — 시도 분포.** 세션당 시도 횟수, 첫 클리어까지의 중앙 시도 횟수, `abort` 이전
시도 횟수 분포. brief 의 중단 판정이 여기서 읽힌다.

**그림 — 코스 지도 위의 사망 히스토그램.** `tests/verify/course-map/` 파이프라인이 이미
생존 회랑을 그리므로, 그 위에 `k*` 밀도를 겹치면 끝이다. **솔버가 예측한 최난 구간과
사람이 실제로 죽는 구간이 겹치는지**가 한 장에서 읽힌다.

### 7.1 판정 규칙 (초안)

- **표본 바닥**: 섹터당 **진입** 30건, 스테이지당 시도 20건 미만이면 판정 보류.
  구현에서 바닥을 사망이 아니라 진입으로 바꿨다 — 진입 174 에 사망 0 이면 "여기서는 안
  죽는다"가 충분히 서는데, 사망 수로 재면 그 행이 영원히 보류로 남기 때문이다.
  3명으로는 섹터별 판정이 서지 않는다는 것은 그대로다.
- 한 섹터가 그 티어 사망의 40% 이상 → 재큐레이션 대상.
- 여유가 더 큰 밴드의 사망률이 더 작은 밴드보다 높다 → **솔버가 못 보는 요인**이 있다
  (시각적 오독, 리듬, 게이트 직후의 인지 부하). 섹터 도형을 의심할 자리다.
- 첫 클리어까지의 중앙 시도 횟수가 티어 순서와 어긋난다 → 티어 곡선이 수치상 단조여도
  실제로는 뒤집혀 있다.
- `gd` 중앙값이 큰 섹터 → 미세 조작 실패가 아니라 **경로 판단 실패**다. 폭을 넓힐 것이
  아니라 선행 가시성이나 형상 가독성을 봐야 한다.

### 7.2 분석기 자체의 검증

- 재구성한 빌드와 이벤트의 `bld` 가 일치하는가. 불일치율이 0 이 아니면 즉시 조사.
- 이벤트의 `gw`·`gd` 가 재구성한 자유 구간에서 다시 계산한 값과 일치하는가.
- (2차) `tail` 표본에서 궤적이 실제로 `S` 를 벗어난 지점과 `k*` 의 거리 분포. 이 거리가
  작아야 §1.1 의 상계가 쓸모 있다.

둘 이유가 없어졌다. 다만 §1·§3 의 스키마 규율은 그대로 지킨다 — 배관은 언제든 갈아
끼우지만 스키마가 틀리면 모은 데이터를 버린다.

**2차 — 분석기. (완료, 0.5.7)** 표 A~D 와 그림. `tools/death-report/` 에 있고
`README.md` 가 세 걸음(pull → report → figure)을 적어 둔다. 재구성 대조는 1차의
`tests/verify/telemetry.ts` 가 24주행에서 불일치 0 으로 확인한다.

구현하며 솔버에 손댄 것이 하나 있다. `SolveTrace` 에 스텝당 상승·하강 이동량(`up`·`down`)을
실었다 — 역추적이 추적만으로 가능해야 분석기가 솔버의 내부 계산을 복제하지 않는다.
그리고 분석기는 조각별 추적을 이어 붙여 **코스 전체 회랑**을 다시 구한다. 솔버의 B[k] 는
그 조각 끝까지의 생존이라 조각 경계 근처에서 S 가 크게 부풀고, 보정 없이는 `k*` 가
사망 지점에 붙는 것이 지오메트리 때문인지 계산 방식 때문인지 가릴 수 없었다.

**3차 — 표 B 로 티어 목표치 재보정.** 이 기능이 존재하는 이유.

`brief.md` 는 건드리지 않는다. 수집은 게임의 문법도 시선 예산도 바꾸지 않는다.
`spec.md` 의 3단계 비목표에 있는 "계정 동기화·리더보드"도 그대로 유효하다 — 이 기능은
계정을 만들지 않고, 모은 데이터를 기록에 쓰지 않는다(§4.5).

## 9. 열린 질문

1. **`tail` 표본을 3차에 넣을 것인가.** §1.1a 때문에 필요해졌지만, 같은 측정이 한편으로
   "사망 x 집계로 충분하다"고도 말한다. 표 A 가 한 섹터를 지목하고 그 안에서 상류 원인을
   따져야 할 때 넣는 것이 낫다고 본다.
2. 수집 기본값 켬/끔. §6 은 켬을 권하지만 판단이다. 끔이 기본이면 §2 의 이탈률은
   사실상 못 잰다는 것이 대가다.
3. Blob 스토어를 wave-runner 전용으로 둘지 레포 공용으로 둘지. 경로에 `<project>` 가
   있으므로 공용 하나로 충분하지만, 한도 잠금(§4.5)이 프로젝트 전체로 번진다.
4. 레이트 리미터가 인스턴스 메모리다. 서버리스라 인스턴스가 늘면 실효 상한도 같이
   는다 — 막으려는 것이 폭주 루프이므로 지금은 충분하지만, 공개 트래픽이 붙으면
   상태를 둘 곳이 필요해진다.

## 10. 배포 전에 할 일

1. Vercel 프로젝트에 **비공개 · `icn1`** Blob 스토어를 연결한다(`BLOB_READ_WRITE_TOKEN`
   자동 주입). **지역과 공개/비공개는 만든 뒤에 바꿀 수 없다.** 공개 스토어는 URL 만 알면
   누구나 읽고, 지역은 쓰기가 CDN 캐시를 타지 못하므로 함수와 붙어 있어야 한다 —
   `vercel.json` 의 `regions` 와 라우트의 `preferredRegion` 이 같은 `icn1` 이다.
   바꿀 수 있는 쪽(함수)이 못 바꾸는 쪽(스토어)에 맞추는 것이 순서다.
2. 필요하면 `TELEMETRY_PROJECTS` 를 설정한다. 비워 두면 `wave-runner` 만 허용된다.
3. 로컬에서 `vercel link` 를 해 둔다 — 확인 경로(§4.4)가 OIDC 로 인증한다.
4. 주 1회 `pull.sh` 로 덤프해 레포 밖에 보관한다(§4.5). **한도 잠금은 내보내기도 막는다.**
