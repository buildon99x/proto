# Smash Rally 3D — 웹 배드민턴 게임 통합 개발 스펙

> **문서 식별자**: `SMASH-RALLY-WEB-SPEC`  
> **버전**: `v1.0`  
> **작성일**: 2026-10-14 (KST)  
> **프로젝트**: 배드민턴 게임  
> **상태**: 초기 개발 기준안(구현·플레이 테스트를 통해 수치 조정)

## 0. 한 페이지 핵심 요약 — 절대 놓치지 말아야 할 것

이 게임은 **닌텐도 스위치 스포츠 배드민턴의 빠른 랠리와 짜릿한 타격 경험**을 기준으로, **PC 마우스와 모바일 터치만으로 즐기는 3D 아케이드 배드민턴**을 만드는 프로젝트다. 롤모델의 게임 경험과 메커니즘을 연구하되 캐릭터·애니메이션·UI·사운드·자산을 복제하지 않는다.

### 0.1 품질 우선순위 — 절대적인 순서

1. **랠리 성립**: 서브 → 이동 → 타격 → 비행 → 상대 리턴 → 실점이 일관되고 반복 가능해야 한다.
2. **입력 신뢰성**: 클릭/터치가 의도한 샷으로 발동하고, 정확한 방향으로 날아가야 한다. 예측 불가능한 오조작은 금지한다.
3. **배드민턴다운 셔틀콕**: 강한 공기저항, 초기 급가속, 비행 중 감속, 낙하와 네트 충돌이 설득력 있어야 한다.
4. **타격감**: 몸통-팔-라켓 애니메이션, 실제 타격 시점, 셔틀 반응, 충격음, 카메라/FX가 **같은 접촉 순간**에 맞물려야 한다.
5. **샷의 전략성**: 클리어·드라이브·드롭·스매시·슈퍼 스매시가 각각 전술적인 용도가 있고 서로 다른 궤적을 보여야 한다.
6. **자연스러운 자동 이동과 풋워크**: 캐릭터가 순간이동하지 않고, 예상 낙하지점까지 움직이며 회복동작을 수행해야 한다.
7. **공정한 AI와 심리전**: 상대도 시간·거리·도달 가능성의 제약을 받고, 빈 공간 공략과 전후좌우 교란이 성립해야 한다.
8. **웹 접근성과 성능**: 설치 없이 로딩, PC·모바일 조작, 최소 30fps 저사양 폴백, 기본 모바일 UX가 보장돼야 한다.

**핵심 금지사항**: 단지 셔틀콕을 빠르게 이동시키는 것만으로 스매시를 구현했다고 간주하지 않는다. 단순 점프모션만 붙이고 랠리와 타격 판정이 부정확해도 완료로 간주하지 않는다. 점수·스킨·메뉴가 있어도 위 8개 조건을 통과하기 전에는 코어 완성으로 간주하지 않는다.

### 0.3 제품 성공을 가르는 실제 플레이 질문

- 플레이어가 **3회 안에 기본 조작을 이해**하고 자연스럽게 랠리를 시작하는가?
- 좋은 타이밍에 스매시를 쳤을 때 **소리만 강해진 게 아니라** 몸·라켓·셔틀 비행·상대 수비에서 차이가 나타나는가?
- 좌측 깊은 클리어 → 우측 네트 드롭 → 중앙 스매시처럼 **의도된 전술**이 실제 경기에서 작동하는가?
- 실패했을 때 **늦게 눌렀는지 / 위치가 닿지 않았는지 / 네트에 걸렸는지** 플레이어가 이해할 수 있는가?
- 모바일 브라우저에서 화면의 작은 셔틀콕을 정확히 탭하지 않아도 재미가 유지되는가?

## 2. 게임플레이 루프와 경기 규칙

### 2.1 플레이 루프

```text
메인 메뉴 → 빠른 경기 → 서브
  ↓
상대가 타격 → 셔틀 비행 / 예상 접촉 위치 갱신
  ↓
우리 캐릭터 자동 이동 (가속, 감속, 풋워크)
  ↓
플레이어: 공격 방향 + 샷 종류 + 타이밍 입력
  ↓
타격 판정 / 스윙 애니메이션 접촉 / 타격 FX·SFX 동기화
  ↓
셔틀 비행 → 상대의 위치 예측 및 수비 → 다음 랠리
  ↓
착지 / 아웃 / 네트 / 미스 판정 → 점수 → 다음 서브
  ↓
5점 선취 → 결과 → 재대결
```

### 2.2 MVP 경기 규칙(아케이드)

- 1 vs AI, **5점 선취 단판**. 동점이더라도 5점 선취로 종료하는 간략 룰을 MVP 기본값으로 사용하며 테스트 후 변경 가능.
- 한 번의 랠리 승리 시 1점. 라인에 걸치면 인(IN). 공식 단식 코트의 기본 경계선을 따른다.
- 네트 미통과, 자기 코트 착지, 상대측 코트 바깥 낙하, 헛스윙 후 낙하 시 실점.
- 서버 교대: 랠리 승자가 다음 서브. 복잡한 서비스 폴트는 MVP에서 완화하고, 짧은 서비스·대각 서비스 규칙은 추후 엄격 모드에 추가.
- **실제 배드민턴의 공식 득점 방식과 동일하다고 표기하지 않는다.** 빠른 플레이를 위한 아케이드 규칙이다.
- 일시정지, 다시 시작, 오디오 설정은 첫 버전부터 제공한다.

### 2.3 주요 게임 상태(State Machine)

`BOOT → MENU → COUNTDOWN → SERVE_READY → SERVING → RALLY → POINT_RESOLVED → (SERVE_READY | MATCH_FINISHED) → RESULTS`

- RALLY 안의 셔틀 상태: `IN_FLIGHT | CONTACT_PENDING | CONTACTED | DEAD`.
- 플레이어 상태: `IDLE | READY | TRACKING | FOOTWORK | PREPARE_SWING | SWING | RECOVER | LUNGE | DIVE`.
- 프레임별 직접 판정이 아닌, **명시적 이벤트를 통해 상태 전이**한다. 1회 셔틀 접촉에 1회 타격만 허용한다.

## 3. 코트·월드·카메라

### 3.1 좌표 체계

- **단식 코트 실제 비율**: 길이 13.40 m, 폭 5.18 m. 인게임 1단위 = 약 1m. 네트는 코트 중앙 `z=0`.
- X축: 좌↔우(`-2.59` ~ `+2.59`), Z축: 앞↔뒤(`-6.70` ~ `+6.70`), Y축: 높이.
- 네트 중심 높이 약 1.524m, 지주 높이 약 1.55m. 모델과 충돌 판정을 분리한다.
- 자기 편을 `z < 0`, 상대편을 `z > 0`으로 표시. 선수의 위치 및 카메라 반전은 진영 설정 값으로 일반화한다.
- MVP는 싱글 경계선만 판정하며 복식용 추가 라인은 미관 요소로만 표시할 수 있다.

### 3.2 코트 품질

- 시야에서 라인/네트/셔틀과 캐릭터가 분명히 구분돼야 한다.
- 셔틀이 조명·바닥 색에 묻히지 않도록 크기/대비/꼬리 잔상을 보정하되, 실제 물리적 충돌 판정은 별도로 유지한다.
- 바닥 그림자와 간결한 3D 관중석으로 스포츠 경기장 분위기 연출.
- 모바일 저사양에서 네트 메시와 그림자가 깜빡이지 않도록 기본 LOD 제공.

### 3.3 카메라

- 기본: 자기 진영 뒤쪽·높은 위치의 **3인칭 스포츠 방송 카메라**. 양쪽 코트의 핵심 착지 지점이 항상 보이도록 한다.
- 세로축 깊이감과 착지지점을 읽을 수 있도록 적절한 기울기와 렌즈/시야각 사용. 초기 예: 수직 FOV 45~55°(확정값 아님).
- 화면 흔들림은 스매시 순간에만 40~80ms 내외로 작게 제공하고 **설정에서 끌 수 있어야** 한다.
- 기본 경기 중 급격한 줌/컷/카메라 회전 금지. 초보자의 공 추적을 방해하지 않는다.
- 화면비: PC 16:9 우선, 모바일 16:9 가로형 권장. 터치 대상·HUD는 노치/안전영역 및 작은 화면을 고려.
- 자동 화면 방향 전환이 불가능한 브라우저에서는 강제가 아니라 가로 사용 안내를 표시한다.

## 4. 입력 UX — 가장 중요한 설계 결정 중 하나

### 4.1 공통 원칙

- **이동은 자동**이다. 플레이어는 `어디로 칠지(목표)` + `어떤 샷인지(종류)` + `언제 칠지(타이밍)`에 집중한다.
- 실제 셔틀콕을 탭하는 게임이 아니라 **상대 코트의 목표 착지 지점을 조준**하는 게임이다.
- 입력 액션은 단일 형식 `ShotCommand { shotIntent, target, issuedAt, pointerType }`으로 정규화한다.
- 목표 지점은 상대 코트와 카메라 레이캐스트로 결정하고, 유효하지 않은 클릭은 가장 가까운 합법 목표점으로 클램프한다.
- **조준 방향과 결과의 인과성 우선**: 타이밍이 나쁘다고 공격 목표의 좌/우가 임의로 역전되어선 안 된다.
- 버튼 연타의 이점 제한. 한 접촉 기회에 **마지막 유효 단일 명령** 또는 첫 유효 명령 중 어느 것을 사용할지 일관되게 설정한다(초기값: 접촉 임박 시 마지막 유효 명령으로 업데이트, 락 시점 후 변경 불가).
- 입력 버퍼, 스윙 발동, 애니메이션 접촉을 분리하여 저사양 프레임 저하가 입력 판정에 끼치는 영향을 최소화한다.

### 4.2 PC(마우스) 기본 조작

| 입력 | 동작 | 비고 |
|---|---|---|
| 마우스 이동 | 상대편 코트 내 착지 예상 지점 미리보기 | 작은 링/표시로 조준 위치 확인 |
| **좌클릭** | 기본 샷(상황에 따라 드라이브/일반 리턴), 스매시 기회면 스매시 | 가능한 샷 아이콘 강조 |
| **우클릭** | 드롭 샷 | 게임 캔버스 우클릭 기본 메뉴 방지 |
| **Shift + 좌클릭** | 깊은 클리어 | 컨트롤 보조 안내 |
| `Esc` | 일시정지 | 게임 중 외부 입력 방해 금지 |
| 선택적 보조 UI | 화면 하단 샷 버튼(클리어·드롭·기본) | 터치패드/접근성 대응 |

- 기본 좌클릭은 **리턴 상황**에 따른 맥락형 샷이다. 셔틀 높이와 타격 자세가 스매시 조건을 만족하면 스매시로 전환한다.
- **슈퍼 스매시**는 별도 난해한 조합키가 아니라, 약하게 높이 뜬 공을 유효 위치에서 `PERFECT` 타이밍으로 스매시한 결과다.
- 프로 모드에서 수동 샷 선택 고도화는 후속 범위. MVP는 조작 난도를 늘리지 않는다.

### 4.3 모바일(터치) 기본 조작

| 제스처 | 동작 |
|---|---|
| 상대 코트 탭 | 해당 목표 방향에 기본 리턴 / 스매시 가능 시 스매시 |
| 상대 코트에서 **아래로 짧게 스와이프** | 드롭 샷 |
| 상대 코트에서 **위로 짧게 스와이프** | 높은 클리어 |
| 화면 샷 버튼(옵션) | 터치 제스처가 어려운 플레이어 보조 |

- **제스처 시작 위치 = 목표 착지점**, 제스처 방향 = 샷 종류. 따라서 한 손 조작에서 조준과 샷 선택이 분리되지 않고 자연스럽게 수행된다.
- 모바일에서 짧은 스와이프의 종료 시점을 판정 완료 시점으로 볼 경우 입력 지연이 생기므로 `pointerdown`에서 시작 목표/시간을 저장하고, 스와이프 임계치 충족 즉시 커맨드를 확정한다. 탭은 `pointerup`에서 빠르게 구분하되 접촉 전 버퍼로 보정한다.
- 브라우저 스크롤·당겨서 새로고침·길게 눌러 텍스트 선택이 게임 캔버스 동작을 방해하지 않도록 `touch-action: none` 등 적용. 캔버스 외 UI에서는 일반 접근성 유지.
- 작은 화면에는 목표 코트를 **좌·중·우 3개 영역 + 전·중·후 3개 깊이**로 시각 안내하되, 실제 위치 좌표는 연속적으로 사용한다. 이 보조 격자는 옵션.
- 일시정지 버튼은 시야를 방해하지 않는 안전영역 고정 위치에 제공.

### 4.4 입력 타이밍(초기 튜닝값 — 확정 수치 아님)

`contactTime`은 실제 셔틀이 라켓의 유효 히트 존에 도달할 것으로 예측한 시간.

| 판정 | `abs(inputAt - idealInputAt)` | 결과 원칙 |
|---|---:|---|
| PERFECT | ≤80ms | 좋은 속도·낮은 오류·강한 임팩트, 슈퍼 스매시 후보 |
| GOOD | ≤180ms | 정상 리턴 |
| WEAK | ≤300ms | 약한 리턴, 공격권을 넘기기 쉬운 높은 공 |
| MISS | 접촉 범위 이탈·버퍼 만료 | 헛스윙, 리턴 실패 |

- 위 수치는 **입력 시간과 실제 애니메이션 접촉 시점의 관계를 결정한 후** 구현한다. `inputAt`과 `contactTime`을 단순 동일시하면 스윙 동작 시간 때문에 게임이 느껴질 수 있다.
- 예: 스윙 애니메이션 내 실제 `hit_frame`이 시작 후 120ms라면 최적 버튼 입력은 **예상 접촉 120ms 전**으로 안내하는 방식이 가능하다(값은 애니메이션별로 조정).
- 셔틀이 아직 멀리 있는 상태에서 누른 입력은 **유한한 버퍼(초기 350ms 전후)**에 보관. 너무 이른 입력은 임의 타격으로 바꾸지 않고 피드백 제공.
- 초보자 모드는 타이밍 창 확대 및 약한 리턴의 성공률 상승. 고급 모드는 기본값과 정밀 타이밍을 유지.
- 타이밍 판정과 실제 도달 가능성 판정은 별개다. **상대편 코트 어디서든 누르면 무조건 리턴되는 게임은 금지**한다.

### 4.5 입력 상태의 시각적 피드백

- 셔틀이 접근하면 캐릭터 발밑 타이밍 링, 짧은 사운드 큐와 준비 애니메이션 표시.
- 타격 후 `PERFECT / GOOD / WEAK`, 실패 시 `TOO EARLY / TOO LATE / OUT OF REACH`처럼 **원인 중심 메시지** 출력.
- 기본 샷이 스매시로 승격되는 상황에서는 조준/샷 UI의 작은 아이콘이 바뀐다. 장시간 전체 화면을 덮는 팝업 금지.

## 5. 셔틀콕 물리·샷 시스템 — 핵심 엔진

### 5.1 물리 모델

일반 공의 등속 수평 운동이나 공중 포물선 단일 보간으로 구현하지 않는다. **중력 + 속도에 따른 큰 항력**으로 셔틀콕의 비행을 계산한다.

```text
v_rel = velocity - windVelocity   // MVP windVelocity = 0
a = gravity - dragK * |v_rel| * v_rel
velocity += a * fixedDt
position += velocity * fixedDt
```

- `dragK`는 실험 값으로 보정하는 유효계수(질량/면적/항력계수를 합친 게임용 값). 출발점이 아닌 **튜닝 파라미터**로 둔다.
- 고속 스매시는 초기에 매우 빠르되 거리와 함께 급감속해야 한다. 셔틀콕의 꼬리/콜크 방향은 비행속도 방향으로 보간해 표시한다.
- `fixedDt` 1/120초를 초기 권장으로 검토하고, 성능 문제 시 1/60초 + 연속 충돌 검출(CCD)을 사용한다. 렌더 프레임과 물리 스텝 분리.
- 프레임 스파이크 시 누적 시간과 최대 서브스텝 수에 상한을 두어 시뮬레이션 폭주를 방지한다.
- 바닥/네트 통과 충돌은 **이전 위치→현재 위치 선분(스윕)**을 사용해 고속 셔틀이 얇은 네트를 통과하지 못하도록 한다.
- 시각 메시는 확대/잔상을 적용하더라도 실점 판정은 셔틀의 콜크 기준 충돌 프록시로 처리한다.
- 공의 물리/애니메이션/착지 예측을 서로 다른 독립 계산으로 구현하지 않는다. **같은 물리 함수**로 실제 비행과 예측을 모두 실행한다.

### 5.2 샷 데이터 모델과 전략적 차별화

| 샷 | 주된 역할 | 궤적·비행 | 리스크/반격 구조 |
|---|---|---|---|
| **클리어(Clear)** | 시간 확보, 상대를 뒤로 밀기 | 높게 떠서 깊게 낙하 | 짧아지면 상대 스매시 기회 |
| **드라이브(Drive)** | 빠른 수평 랠리·좌우 압박 | 낮고 빠른 궤적 | 각도가 너무 낮으면 네트 위험 |
| **드롭(Drop)** | 앞쪽 빈 공간·전후 교란 | 네트 직후 급격히 낙하 | 느리거나 높으면 상대가 잡아챔 |
| **스매시(Smash)** | 공격 마무리 | 높이 있는 접촉점에서 가파른 고속 하강 | 몸이 무리하면 회복이 늦음 |
| **슈퍼 스매시(Super Smash)** | 명확한 공격 기회 보상 | 높은 접촉 + 완벽한 타이밍의 가장 강한 하강 | 매 샷 사용 불가, 공격 기회 필요 |

- **슛 궤적은 이 샷 타입별로 실제로 달라야** 한다. 모든 샷이 속도만 다른 동일 곡선이면 실패.
- 클리어/드롭/스매시의 목표 좌표는 모두 플레이어가 지정하는 상대편 유효 영역과 연결된다.
- 근거리 드롭이 과도하게 강력해지는 문제는 비행시간·접근 가능한 위치·AI 회복 능력으로 조정한다. 가짜 확률로 성공을 막지 않는다.

### 5.3 목표 착지 지점 역산(Trajectory Solver)

1. 접촉 위치 `start`, 목표 착지 좌표 `target`, 샷 타입을 결정.
2. 샷별 목표 도착 시간/높이/네트 통과 마진의 **허용 범위**를 읽음.
3. 여러 초기 속도 벡터 후보를 생성하고 **동일 항력 시뮬레이터**로 비행을 예측.
4. 목표와의 거리 오차, 네트 통과, 현실적인 타격 속도, 최고점 등을 평가해 최적 후보 선택.
5. 불가능한 명령은 가장 가까운 가능한 착지점 또는 약한 리턴으로 제한. 조준 표시에서 한계를 예고한다.
6. 실제 비행 초기 속도를 적용하고, 결과가 목표와 얼마나 가까운지 자동 회귀 테스트.

**구현 주의**: 공기저항이 강하므로 단순 포물선 해석식만으로 목표 착지를 정확히 맞출 수 없다. 사전 계산 샷 후보 라이브러리 + 수치 탐색을 권장한다.

### 5.4 타격 유효 조건

- 캐릭터와 셔틀의 3D 거리, 셔틀 높이, 해당 애니메이션의 접촉점, 선수 진행 방향, 스윙 상태를 모두 검사한다.
- 스매시는 **높은 접촉점**이 있는 경우에만 허용한다. 낮은 셔틀은 강한 공격을 강제로 발동시키지 않는다.
- 슈퍼 스매시는 `스매시 유효` + `약하게 뜬 높은 공` + `PERFECT` + `타격가능 거리`를 모두 만족해야 한다. 초기 높이·속도 임계치는 전부 JSON/TS 설정으로 튜닝 가능하게 한다.
- 헛스윙, 네트, 아웃은 실제 결과로 결정한다. 특정 득점을 만들기 위한 결과 조작 금지.
- 소리·충격 FX의 원천 이벤트는 **`shuttle:hit` 단 하나**. 발동 판정과 발행 시점 중복 금지.

### 5.5 좌표/판정 테스트 기준

- 라인 접촉 = IN, 경계 바깥 = OUT.
- 셔틀이 네트 평면을 통과할 때 콜크 충돌 프록시가 네트 아래/메시에 닿으면 네트 오류 처리.
- 경기장/엔진 단위 좌표가 명시적으로 일치해야 한다(코트 스케일에 비례한 착지점).
- **물리 기준 테스트 1,000샷 이상** 자동 재생: 네트 통과/좌우 방향/착지 유효성/예측-실제 오차를 기록.
- 회귀 사례: 장거리 클리어, 네트 바로 뒤 드롭, 측면 스매시, 매우 빠른 스매시, 긴 랠리, 프레임 하락 상황.

**물리 연구 참고**: [A Study of Shuttlecock’s Trajectory in Badminton](https://pmc.ncbi.nlm.nih.gov/articles/PMC3761540/), [Shuttlecock velocity decay after smash and slice shots in badminton (2026)](https://doi.org/10.1088/1402-4896/ae5361).

## 6. 캐릭터 자동 이동·풋워크·회복

### 6.1 자동 이동 알고리즘

1. 셔틀콕 비행 상태를 일정 간격으로 앞서 시뮬레이션하여 **도달 가능한 접촉 후보**를 계산.
2. 선수 현재 위치·최고 이동 속도·가속·방향 전환·스윙 준비 시간으로 **도달 가능 여부** 판단.
3. 가능한 후보 중 좋은 리턴 자세/시간 여유를 만드는 인터셉트 포인트 선택.
4. 위치 목표에 맞춰 애니메이션(제자리 대기 → 사이드스텝 → 런 → 런지 → 리턴)을 실행.
5. 타격 뒤 복구 위치는 경기 전략/난이도에 따라 코트 중앙 근처로 서서히 이동.

### 6.2 지켜야 할 조건

- 유저 캐릭터와 AI 모두 같은 기본 이동 제약을 준수한다.
- **순간이동 금지**, 발 미끄러짐 최소화, 이동 속도와 애니메이션 속도 매칭.
- 캐릭터가 놓치면 자연스럽게 다이빙/런지 또는 포기 애니메이션이 나온다. 도달 불가인데 적중 처리 금지.
- 어려운 공을 받은 뒤 회복 지연·균형 무너짐 등으로 다음 공격에 취약해져야 한다.
- 과도한 자동 보정 때문에 플레이어가 오른쪽으로 보냈는데 상대가 항상 중앙으로 즉시 복귀해 전략이 무력화되는 상황 금지.
- 초보자 난이도에서만 선수 이동 여유·접촉 범위를 조금 확대한다. 이동 중 셔틀 위치 추적 성능이 극단적으로 올라가선 안 된다.

### 6.3 필요한 최소 애니메이션 묶음

`Idle/Ready`, `SplitStep`, `Run_Fwd`, `Run_Back`, `Shuffle_Left`, `Shuffle_Right`, `Lunge_Left`, `Lunge_Right`, `Clear_FH/BH`, `Drive_FH/BH`, `Drop`, `Smash`, `JumpSmash`, `Dive`, `Recover`, `Celebrate`, `Miss`, `Serve`.

- MVP에는 우선 사용 빈도가 높은 **Ready / SideStep / Run / BasicHit / Drop / Clear / Smash / Recover / Serve**를 완성하고, 타격 동작의 자연스러운 상·하체 연결을 먼저 확보한다.
- `hit_frame`을 애니메이션 이벤트로 등록하고 타격 판정/물리 이벤트와 연결한다. 임시 이벤트 없이 모션 시작 시 셔틀이 즉시 튀어나가는 구현은 최종 허용하지 않는다.
- 라켓 접촉 포즈와 실제 공 위치가 크게 어긋나면 장르 완성도가 무너진다. IK/어깨·손목 보정은 고도화 단계에서 적용.

**공식 문서**: [PlayCanvas Anim Events](https://developer.playcanvas.com/user-manual/animation/anim-events/).

## 7. 타격감·사운드·VFX 명세

### 7.1 타격 순간의 6개 계층

| 계층 | 요구사항 | 우선순위 |
|---|---|---|
| 스윙 사전동작 | 발 디딤 → 골반·몸통 회전 → 팔/라켓 가속 | P0 |
| 접촉 동기화 | `hit_frame` ↔ `shuttle:hit` ↔ 실제 방향/속도 변화 | **P0 최우선** |
| 충격음 | 클리어/드롭/드라이브/스매시 분리, 거리/강도에 맞는 음량 | P0 |
| 시각 충격 | 짧은 라켓 잔상/셔틀 속도선/임팩트 플래시 | P0 |
| 카메라 반응 | 스매시에만 짧은 shake·미세 줌, 접근성 Off | P1 |
| 상대 반응 | 빠른 공을 받을 때 런지/급수비/균형 회복 | P0 |

### 7.2 이벤트 타임라인(개념)

```text
T-300~150ms: 준비 발동 / 풋워크 / 어깨와 라켓 가속
T=0ms:        유효 라켓 접촉 1회 확정 (결정적 이벤트)
                ├─ 셔틀 초기 속도 벡터 설정
                ├─ SFX: impact + whoosh end
                ├─ VFX: impact frame / trail
                ├─ 짧은 카메라 반응(선택)
                └─ 조준/판정 UI 갱신
T+60~200ms:   팔로스루 / 상대 반응 시작 / 복구 자세
```

- **지속적인 타격 정지(hit-stop)**는 실시간 스포츠 궤적을 훼손할 수 있으므로 게임 전체 시뮬레이션을 정지하지 않는다. 20~40ms 이내의 시각적 임팩트 감각은 애니메이션 재생률/FX/음향으로 표현하고 네트·셔틀 물리는 계속 진행한다.
- 과한 화면 흔들림, 과도한 파티클, 모바일 시야 가림 금지.
- `PERFECT` 스매시에는 고역 라켓 타격 + 낮은 충격 음향 레이어, 짧은 강조 잔상. 기존 스포츠 효과음 무단 복제 금지.
- 효과 구현보다 **A/V 동기화 오차 감소**를 우선한다. 모바일 스피커와 블루투스 이어폰 등 환경에 따라 음향 지연이 다를 수 있어 오디오 언락 후 테스트.

## 8. 상대 AI 설계 — 실제 심리전이 생겨야 함

### 8.1 상태 머신

`READY → READ_TRAJECTORY → SELECT_INTERCEPT → MOVE → CHOOSE_SHOT → PREPARE_HIT → HIT → RECOVER`

AI는 유저와 **동일한 셔틀 물리/접촉/샷 솔버**를 사용한다. 전능한 궤적 수정이나 선수 순간이동 금지.

### 8.2 전술 로직

- 현재 플레이어 위치 및 전후좌우 이동 거리, 직전 리턴의 품질, 상대 회복 중 여부를 관찰.
- 상대의 빈 공간에 드롭/클리어, 중간 빠른 드라이브, 뜬 공을 스매시로 응수.
- 전술 패턴: `후방 클리어 → 전방 드롭`, `왼쪽 드라이브 → 오른쪽 드라이브`, `약한 리턴 유도 → 스매시`.
- 반복 동일 공격을 감지해 어느 정도 적응하되, 숨겨진 절대 명중률/무적 보정 금지.
- AI의 타이밍 오차·착지 정밀도·반응 지연을 **난이도별 튜닝 가능 데이터**로 노출.

### 8.3 난이도(초기 예시, 플레이 테스트 후 조정)

| 등급 | 반응 지연 예시 | 샷 선택 | 기본 성향 |
|---|---:|---|---|
| EASY | 450~650ms | 대부분 안전 리턴, 단순 패턴 | 랠리 3~5회 이상 학습을 지원 |
| NORMAL | 250~400ms | 빈 공간 공략·가끔 드롭/스매시 | 게임 기본 재미 기준 |
| HARD | 140~260ms | 압박·패턴 교란·공격권 활용 | 도달 가능 거리·리커버리 제약은 유지 |

- 모든 수치는 현재 설계 가정. 실제 플레이 평균 랠리 횟수·실점 원인·승률을 계측해 조정한다.
- AI가 상대방 셔틀의 미래 전체 궤적을 '모든 조건에서 완벽히' 알지 않도록 인지 지연과 예상 오차를 도입한다.

## 9. UX·HUD·피드백

### 9.1 게임 화면 정보 우선순위

1. 셔틀 / 플레이어 / 상대 / 네트 / 유효 경계선
2. 예상 수비·공략 위치 정보(과하지 않은 착지 표시)
3. 스윙 가능 시점과 타이밍 신호
4. 상단 점수 / 서브 표시 / 일시정지
5. `PERFECT`, `OUT`, `NET`, `POINT` 같은 간결한 반응 텍스트

### 9.2 필수 화면

- 시작 화면: `빠른 경기`, `조작법`, `설정`.
- 경기 중: 점수(좌측/우측), 일시정지, 타이밍 피드백, 조준 표시.
- 일시정지: `계속`, `다시 시작`, `메뉴`, `사운드`, `FX 강도`, `카메라 흔들림`.
- 결과: 승패, 최종 점수, `다시 경기` 버튼 우선.
- 로딩/오류: 그래픽 기능 미지원, 에셋 로딩 실패, 오디오 시작 안내.
- 최초 실행 30초 튜토리얼: `클릭/탭 → 방향`, `클리어`, `드롭`, `스매시 타이밍` 순서.

### 9.3 접근성

- 카메라 흔들림, 플래시, 궤적 잔상 On/Off 또는 강도 설정.
- 색각 구분을 색상만으로 하지 않고 아이콘/형태/문구 병행.
- 사운드가 없어도 타격 판정·서브 상태 인지 가능.
- 모바일 큰 터치 영역, 작은 조준 오차 흡수, 샷 버튼 대안 제공.
- 오디오 자동재생 제한 때문에 첫 사용자 제스처 이후 Web Audio를 활성화.

## 10. 아트·3D 자산 가이드

### 10.1 비주얼 방향

- 밝고 선명한 **세미 카툰 3D**, 과장된 기럭지/표정은 허용하되 동작 무게중심과 라켓 궤적은 실제 스포츠 느낌.
- 스포츠 방송 카메라에서 식별성이 높은 유니폼 대비, 코트 라인, 라켓 테두리, 흰색 셔틀.
- 중간 수준의 PBR, 원거리 관중은 저비용 배경/실루엣으로 구현. 불필요한 극사실주의 추구 금지.

### 10.2 필요 자산

| 자산 | MVP 요구 | 포맷 |
|---|---|---|
| 실내 코트/네트/라인 | 1세트 | GLB/glTF |
| 플레이어 캐릭터 | 동일 리그의 색상 변형 2명 | GLB + 공통 리그 |
| 라켓 | 1종, 자산 독립 | GLB |
| 셔틀콕 | 1종, 메쉬는 충돌체와 분리 | GLB |
| 핵심 애니메이션 | 9종 이상 / 이벤트 프레임 정의 | GLB 애니메이션 |
| 충격 SFX | 기본, 드롭, 드라이브, 클리어, 스매시, 슈퍼 | OGG/MP3 등 웹 호환 |
| UI/타이밍 표시 | 버튼/아이콘/폰트 | SVG/PNG/WebP/HTML-CSS |
| 이펙트 | trail, impact, shadow, landing | 텍스처/셰이더 |

### 10.3 저작권 / 라이선스

- Nintendo 캐릭터, 경기장 UI, 음원, 애니메이션, 텍스처를 직접 추출/복제하지 않는다.
- 외부 모델·음향·폰트는 라이선스와 출처를 `assets/LICENSES.md`에 기록.
- AI 생성 에셋은 사용 권한, 상표/캐릭터 유사성, 성능과 게임 내 실제 모습을 별도 QA.

| 저장소 | GitHub | 변경 추적, 브랜치, 리뷰, CI |

### 11.3 핵심 데이터 계약 (예시 — 코드 구현 시 세부 타입 수정 가능)

```ts
type ShotType = 'clear' | 'drive' | 'drop' | 'smash' | 'superSmash';
type HitQuality = 'perfect' | 'good' | 'weak' | 'miss';
type RallyPhase = 'serveReady' | 'rally' | 'pointResolved';

type Vec3 = { x: number; y: number; z: number };
type TargetXZ = { x: number; z: number };

interface ShotCommand {
  shotIntent: 'default' | 'clear' | 'drop';
  target: TargetXZ;
  issuedAtMs: number;      // 퍼포먼스 시계 기준
  pointerType: 'mouse' | 'touch' | 'keyboard';
}

interface HitContext {
  shuttlePosition: Vec3;
  shuttleVelocity: Vec3;
  actorPosition: Vec3;
  predictedContactAtMs: number;
  reachability: 'reachable' | 'lunge' | 'unreachable';
  highAttackOpportunity: boolean;
}

interface HitResult {
  shotType: ShotType;
  quality: HitQuality;
  initialVelocity: Vec3;
  target: TargetXZ;
  contactAtMs: number;
}
```

**불변 조건**:

- 게임 상태에 있는 셔틀은 한 랠리에 1개.
- 유효 타격이 없으면 다음 비행 초기 속도를 임의 설정하지 않는다.
- 네트/바닥/아웃/라켓 접촉 판정은 고정 시뮬레이션에서만 갱신.
- UI와 SFX는 물리 결과 이벤트를 구독하고, 물리 결과를 역으로 바꾸지 않는다.
- 디바이스별 입력은 **공통 `ShotCommand`**로 변환하며 서로 다른 게임 로직을 두지 않는다.
- AI와 플레이어는 동일한 `TrajectorySolver`/`HitSystem`을 사용한다.

## 12. 브라우저 성능·적응형 품질

### 12.1 기본 타깃(검증할 목표, 보장치 아님)

| 항목 | 목표 |
|---|---|
| PC 최신 Chrome/Edge/Safari | 60fps 유지 목표 |
| 주요 모바일 최신 브라우저 | 60fps 목표, 저사양 30fps 품질 모드 |
| 렌더러 | **WebGL 2 기본**, WebGPU는 추후 선택·폴백 |
| 첫 실행 다운로드 | 가급적 압축 자산 포함 10~20MB 수준 목표 |
| 프레임별 입출력 | 입력 즉시 시각 반응, 타격 이벤트 지연 최소화 |
| 화면비 | 가로형 우선, 태블릿/데스크톱 리사이즈 대응 |
| 메모리 | 가급적 저사양 모바일에서 지속 경기 가능, 전후 GC 스파이크 점검 |

### 12.2 품질 프리셋

- `HIGH`: PC/상위 모바일 — 캐릭터 그림자, 잔상, 전체 코트, 더 많은 이펙트.
- `MEDIUM`: 기본 모바일 — 그림자/포스트 이펙트 제한, 파티클 수 축소.
- `LOW`: 저사양 — 낮은 픽셀비, 고정 카메라, 단순 캐릭터/배경, 음향 핵심 유지.
- 셔틀콕/히트 판정/AI 동작은 프리셋과 무관하게 **동일**해야 한다.
- WebGL 2 미지원 및 GPU 컨텍스트 손실 발생 시 메시지와 재시작 옵션 제공.

### 12.3 모바일·오디오 기술 위험

- 모바일 브라우저의 오디오 정책 때문에 첫 터치 이후 소리를 재생한다.
- 탭·스와이프 인식 시 페이지 스크롤과 게임 컨트롤이 충돌하지 않게 한다.
- 배터리 절전, 낮은 프레임, 브라우저 백그라운드 복귀 시 게임시계와 물리 누적 시간이 폭주하지 않게 일시정지/재개 처리.
- 외부 에셋은 HTTPS·CORS 및 캐시 헤더 확인. 폰트·텍스처·SFX 로딩 실패에도 명확한 fallback 제공.

**공식 문서**: [PlayCanvas 지원 브라우저](https://developer.playcanvas.com/user-manual/engine/supported-browsers/).

## 13. 배포·릴리스 명세

### 13.1 기본 배포: Vercel

```bash
# 공식 create-playcanvas에서 Engine + Vite + TypeScript 형식 선택
npm create playcanvas@latest
cd smash-rally-3d
npm install
npm run dev

# 프로덕션 빌드
npm run build
```

- 공식 생성기 사용. 생성 시 요구되는 Node.js 버전을 확인한다(2026-10 기준 공식 가이드는 `22.23.2+`).
- GitHub 저장소에 커밋. Vercel 프로젝트에서 해당 저장소 연결.
- `Build Command = npm run build`, `Output Directory = dist`, Framework = Vite.
- 메인/PR 환경에 Preview URL 생성. 공개 배포 전 스마트폰 실기기 연동 검증.
- MVP는 정적 웹 게임이라 서버리스 API·DB·게임 매치메이킹 서버가 필요하지 않다.
- 저장·설정은 브라우저 로컬 저장(클라이언트 데이터 삭제 가능성 안내).

### 13.2 보조 배포: ChatGPT Sites(GPT 사이트)

- Sites는 웹·경량 앱·게임 게시를 지원하지만 **PlayCanvas/WebGL 프로젝트의 특정 호환성은 별도 검증이 필요**하다.
- 구현/배포의 기준은 Vercel로 유지하고, Sites는 첫 플레이어블 빌드를 가져가 렌더링, GLB 로딩, 음향, 프레임·터치 입력을 평가한다.
- 지원되지 않는 런타임/호스팅 제약이 확인되면 Sites를 억지로 맞추지 않고 Vercel을 유지한다.
- **중요: ChatGPT Sites는 관련 정책상 13세 미만 또는 적용 디지털 동의 연령 미만 아동을 대상으로 하는 서비스에 사용할 수 없다.** 해당 대상 게임이라면 Vercel 등 대체 호스팅과 별도 규정 검토가 필요하다.
- Sites 배포 성공을 Vercel 배포의 필수 선행 조건으로 두지 않는다.

**공식 문서**: [PlayCanvas create-playcanvas](https://developer.playcanvas.com/user-manual/getting-started/start-with-create-playcanvas/), [Vercel Vite](https://vercel.com/docs/frameworks/frontend/vite), [ChatGPT Sites 안내](https://help.openai.com/ko-kr/articles/20001339-creating-and-using-chatgpt-sites).

## 14. MVP 개발 단계 · 의존관계 · 산출물

> 아래 일정은 완성된 3D 에셋을 확보하고 1인 개발/AI 코딩 지원을 사용하는 **초기 추정**이다. 품질 완성에 따라 기간 조정.

### M0 — 기술 스파이크(약 2~3일)

- PlayCanvas + TypeScript + Vite 실행; Vercel 정적 Preview 배포 성공.
- 모바일 Safari / Android Chrome에서 3D 코트 1개 렌더.
- 고정 스텝과 터치 이벤트 샘플 검증.
- 완료 기준: 브라우저에서 로딩·렌더·터치 반응 정상, 모바일 그래픽 폴백 확인.

### M1 — 기초 랠리 수직 슬라이스(1~2주)

- 코트, 네트, 셔틀, 물리/착지/아웃, 기본 AI 라켓, 점수 구현.
- 플레이어 자동 이동과 기본 타격, 상대 리턴.
- 완료 기준: **3~5회 이상 랠리 안정적**, 네트/아웃 결과가 납득 가능, 게임 종료와 재시작 가능.

### M2 — 샷·조작·전술(1~2주)

- PC/모바일 조작 정식 구현, 클리어·드라이브·드롭·스매시·슈퍼 스매시.
- 역산 샷 솔버·스매시 기회조건·조준·타이밍 피드백.
- AI EASY/NORMAL/HARD와 위치 전략 구현.
- 완료 기준: 모든 샷이 **눈으로 구분되는 궤적**, 전후좌우 공략 가능, 반응이 사용자 명령과 일치.

### M3 — 타격감·애니메이션(1~2주)

- 접촉 이벤트에 모션·셔틀·SFX·FX 동기화.
- 코트/선수 아트 업그레이드, 다이빙·회복, 임팩트 다듬기.
- 완료 기준: **스매시가 강력하고 명확**하며 모바일에서도 플레이가 가능; 시각/음향/물리 접촉이 맞음.

### M4 — 품질·출시 준비(1~2주)

- UI, 튜토리얼, 오디오 설정, 프레임별 튜닝, 성능 프리셋.
- 자동 회귀 테스트, 모바일/PC 크로스브라우저 QA, 에셋 라이선스 점검.
- Vercel 프로덕션 공개 및 Sites 호환성 실험.
- 완료 기준: 크래시 없는 10회 연속 경기, QA 이슈/회귀 로그 정리, 배포 링크로 접근 가능.

**예상 총량**: 에셋 상황에 따라 약 6~8주 수준의 초기 계획. 기간은 품질을 희생해 고정하지 않는다.

## 15. 테스트 플랜과 수락 기준(Definition of Done)

| ID | 검증 항목 | 통과 조건(초기 목표) |
|---|---|---|
| `QA-01` | 기본 경기 | 시작→서브→3회 이상 랠리→득점→5점 종료→재대결 연속 성공 |
| `QA-02` | 셔틀 물리 | 클리어/드롭/스매시의 궤적·낙하 차이가 명확, 네트 통과/아웃 정확 |
| `QA-03` | 목표 타격 | 좌·중·우 조준이 의도대로 표현되며 임의 방향 반전 없음 |
| `QA-04` | 입력 타이밍 | PERFECT/GOOD/WEAK/MISS 판정이 독립적이고 재현 가능 |
| `QA-05` | 접촉 동기화 | 라켓 모션 접촉 프레임, 속도 변화, SFX/VFX 중복·지연 없음 |
| `QA-06` | 자동 이동 | 도달 불가능한 공을 캐치하지 않고 순간이동 발생하지 않음 |
| `QA-07` | 샷 전술 | 클리어→드롭→스매시 패턴으로 상대를 실제로 흔들 수 있음 |
| `QA-08` | AI 공정성 | 각 난이도에서 추적/회복 제약 유지, 한쪽만 비현실적 보정 없음 |
| `QA-09` | 모바일 입력 | 탭·짧은 위/아래 스와이프 구분, 스크롤·제스처 충돌 없음 |
| `QA-10` | 웹 성능 | 주요 PC 60fps, 대상 모바일 30fps 이상 폴백 목표(실기기 계측) |
| `QA-11` | 안정성 | 10경기 연속 플레이에서 런타임 예외/메모리 급증/물리 발산 없음 |
| `QA-12` | 공개 배포 | Vercel HTTPS 링크 직접 접속·새로고침·모바일 재방문 문제없음 |
| `QA-13` | 자산 | 외부 3D/음원/폰트 자산의 라이선스 확인 |
| `QA-14` | 접근성 | 화면 흔들림/플래시 저감, 기본 무음 상태에도 플레이 정보 전달 |

**성능 계측**: FPS뿐 아니라 프레임타임, 첫 실행 다운로드 용량, 최초 플레이까지 걸리는 시간, 이펙트 실행 시 스파이크, 실기기 오디오/터치 지연을 측정한다.

**플레이 테스트**: 최소 PC 마우스·모바일 양쪽에서 초보/일반 플레이어를 테스트하고 `평균 랠리 길이`, `샷별 사용량`, `실점 이유`, `PERFECT 성공률`, `AI 난이도별 승률`, `재대결 선택률`을 기록한다. 지표 목표는 플레이테스트 후 확정한다.

## 17. Codex 실행을 위한 업무 지시(개발 에이전트용)

> **메인 목표**: 아래 문서를 단일 제품 기준으로 삼아 PlayCanvas Engine + TypeScript + Vite로 실행되는 웹 기반 3D 배드민턴 플레이어블을 만들 것. 기존 구현이 있다면 구조·기능·버그를 먼저 진단하고, 핵심 재미 및 QA-01~QA-14를 우선 개선한다.
>
> 1. 시작부터 거대한 콘텐츠를 만들지 말고 M0→M1→M2→M3→M4 순으로 구현한다.  
> 2. **셔틀 물리·역산 샷 솔버·타격/점수 판정에 자동 테스트**를 붙인다.  
> 3. 샷/플레이어/AI 모두 하나의 물리·타격 규칙을 공유한다.  
> 4. 모든 타이밍과 AI 수치는 코드를 재배포하지 않고 빠르게 조정 가능한 설정 테이블에 모은다(초기에는 코드/JSON 변경 후 빌드로 충분).  
> 5. 플레이어의 마우스·터치 목적지는 반드시 실제 착지 목표에 반영한다.  
> 6. 순간이동·임의 명중·라켓 미접촉 시 공 발사·관전자 혼란 유발 연출을 금지한다.  
> 7. 매 단계에서 실제 브라우저 빌드·실행, 모바일 조작 확인, FPS/오류 검증 결과를 기록한다.  
> 8. 다음 단계로 진행하기 전에 미완료 수락기준과 체감 품질상의 약점을 보고한다.  
> 9. 스펙의 미결정값은 **임시 수치와 변경 이유를 문서에 명시**하여 진행한다.  
> 10. 자산은 라이선스를 확인하고 기존 게임의 고유 표현을 무단 사용하지 않는다.

### 17.1 최초 구현 작업 묶음(우선순위 순)

```text
1. 프로젝트 스캐폴딩 + Vercel Preview
2. 3D 단식 코트/네트/스포츠 카메라
3. 셔틀 고정시간 물리 + 자동 착지/네트 판정 테스트

9. 타격 애니메이션 이벤트 + SFX/VFX 동기화
```

## 20. 완료 정의

이 프로젝트의 첫 성공은 메뉴 화면, 멋진 3D 캐릭터 또는 배포 URL만으로 판단하지 않는다.

> **브라우저에서 PC 마우스 또는 모바일 한 손 조작으로, 자동 풋워크를 하는 3D 캐릭터가 공기저항이 있는 셔틀콕을 정확히 받아 넘기고, 클리어·드롭·스매시로 상대의 빈 공간을 공격하며, 접촉 순간의 애니메이션·물리·사운드가 일치하는 긴장감 있는 1:1 랠리를 반복할 수 있을 때** 비로소 핵심 게임플레이가 완성된 것으로 본다.
