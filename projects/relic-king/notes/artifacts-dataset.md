## 1. 티어 매핑 원칙 (v0.1, 유지)

**현실의 현존 개체 수를 그대로 게임 재고로 쓴다.** 밸런스를 위해 등급을 지어내지 않는다.

| 티어 | 현실 기준 | 게임 재고 | 예 |
| --- | --- | --- | --- |
| T4 유일 | 세상에 단 하나 | 1 | 로제타 석 |
| T3 국보 | 현존 한 자릿수 | 6 | 신라 금관 (실제로 6점) |
| T2 진귀 | 현존 수십 점 | 60 | 청자 상감 매병류 |
| T1 희귀 | 현존 수백~수천 점 | 2,000 | 로마 유리 향유병 |
| T0 흔함 | 현존 수만 점 이상 | 무한 | 상평통보, 데나리우스 |

경계가 애매한 유물은 **더 흔한 쪽으로 내린다.** "유일하다"는 주장이 틀리면 게임의 전제가
무너지지만, 흔한 쪽으로 잘못 놓는 건 아무도 다치지 않는다. G6은 이 원칙 위에 **상태**
축을 별도로 얹었을 뿐, 재고 원칙 자체는 건드리지 않는다(§4).

`types.ts` 변경(구현 시 그대로 반영):

```ts
export type Condition = 0 | 1 | 2 | 3 | 4;
export type SourceStatus = "verified" | "pending";

export type Artifact = {
  // ...v0.1 필드 전부 유지...
  condition: Condition;
  source: string[];
  sourceStatus: SourceStatus;
};
```

`holder`와 `disputed`는 장식이 아니다. 개인이 유물을 캐서 금고에 넣는 구도의 윤리적
리스크를 완화하는 장치다([notes/mda.md §7.1](mda.md)). `source`와 `sourceStatus`는
같은 목적의 연장이다 — "실존"이 전제인 게임에서 데이터 신뢰도 자체도 공개해야 할
규칙이다(척추 5번).

## 3. 유물 종류 분류 — `Shape`를 그대로 쓴다 (신규 분류 미생성)

요청 원문의 "책·그림·도자기 등"은 새 taxonomy를 요구하는 것처�럼 보이지만,
`notes/world-map.md` §8.1이 이미 결정했다: **`Shape` 10종을 그대로 시세 카테고리로
쓰고 새 분류를 만들지 않는다.** 이 문서는 그 결정을 데이터셋 쪽에서도 그대로 따른다 —
가격 카테고리와 유물 종류 분류가 서로 다른 taxonomy면 유물 하나가 두 개의 분류 체계를
동시에 가지게 되어 데이터 모델이 불필요하게 두 배가 된다.

| `shape` | 한국어 분류 | 대표 실제 유형 |
| --- | --- | --- |
| `jar` | 도자기·용기 | 항아리, 매병, 병, 청자·백자·토기 |
| `sword` | 도검·무구 | 검, 창, 갑주 부속 |
| `crown` | 관·머리장식 | 금관, 보관, 왕관 |
| `mask` | 가면·안면상 | 데스마스크, 가면 |
| `scroll` | 문서·서화 | 경전, 필사본, 두루마리, 권자본 회화 |
| `coin` | 화폐 | 동전, 주화 |
| `tablet` | 석판·비문 | 석비, 점토판, 파피루스 |
| `statue` | 조각·상 | 인물상, 신상, 부조 |
| `ornament` | 장신구 | 귀걸이, 목걸이, 흉식, 팔찌 |
| `mechanism` | 기계·기물 | 정밀 기물, 시계, 의기, 등잔대 |

"그림"은 별도 분류를 만들지 않고 `scroll`(권자본 회화·화첩은 전근대 동아시아에서
실제로 두루마리·책자 형태가 대부분이다)로, "책"도 `scroll`로 흡수한다. "도자기"는
`jar`로 흡수한다. 요청이 예로 든 세 범주가 기존 10종 안에서 전부 표현되므로, 새 taxonomy를
만들 이유가 없다는 걸 이 표가 보인다.

## 4. 보존 상태 축 (G6, 신규)

`notes/decisions.md` G6이 정한 상태 5단계를 그대로 쓴다(재정의하지 않음):

```
CONDITION_NAME = ["파손", "보통", "양호", "완품", "관급"]
CONDITION_VALUE_FACTOR = [0.4, 0.7, 1.0, 1.3, 1.6]
평가액 = TIER_VALUE[tier] × CONDITION_VALUE_FACTOR[condition] × valueFactor
```

이 절이 새로 정하는 것은 **각 유물 종의 초기 `condition` 값을 어떻게 매기는가**다.
480종을 손으로 하나씩 판단할 수 없으므로(그 자체가 검증 없는 주장이 된다), 결정론적
공식으로 잡고 1차 자료가 명시적으로 다른 상태를 알려줄 때만 override한다.

```
CONDITION_INITIAL_BASE_BY_TIER = [1, 1, 2, 3, 4] as const   // T0~T4 → 보통/보통/양호/완품/관급
CONDITION_INITIAL_JITTER(artifactId) =
  floor(frac(FNV1a32(`${artifactId}:condition`) / 2^32) * 3) - 1     // -1 | 0 | +1

initialCondition(artifact) = clamp(
  CONDITION_INITIAL_BASE_BY_TIER[tier] + CONDITION_INITIAL_JITTER(id),
  0, 4
)
```

`FNV1a32`는 `notes/world-map.md` §8.2와 동일한 표준 32비트 해시다 — 이 문서도 같은
결정론적 시드 패턴을 재사용한다(새 난수 체계를 만들지 않는다). 근거: 국가·박물관이
소장한 고티어 유물일수록 보존 예산이 크므로 기본값을 티어에 비례해 높게 잡고,
±1 지터로 획일적인 배치를 피한다.

**override 규칙**: 1차 자료가 파손·훼손 사실을 명시하면(예: 화재 피해, 반환 소송 중
손상 등) 공식 결과를 무시하고 실제 상태로 덮어쓴다. override했을 때는 `note`나 수집
커밋 메시지에 근거를 남긴다(§11 확장 규칙의 연장).

상태 저하·복원·습도 효과의 수식은 `spec.md` §9.4에 이미 정의되어 있다(재정의하지 않음).

## 5. `source` 필수 필드·검증 규칙 (G7, 신규)

```
ARTIFACT_MIN_SOURCES = 1               // T0~T3, 신규 상수
T4_MIN_INDEPENDENT_SOURCES = 2         // notes/economy.md §8에 이미 정의됨(재정의하지 않음)
```

- 모든 종은 `source` 배열에 최소 1개의 URL을 가져야 한다. 소장 기관 공식 소장품 페이지,
  국가유산청·문화재청류 공공 DB, 학술 도록·논문을 1순위로 삼는다.
- T4는 **독립 출처 2개 이상**. "독립"의 정의: 서로 다른 발행 주체. 같은 기관의 소장품
  페이지와 보도자료는 같은 주체이므로 1개로 카운트한다.
- `sourceStatus`는 위 기준을 실제로 충족하고 사실 대조를 마쳤을 때만 `"verified"`다.
  네트워크가 차단된 이 실행에서 작성된 항목은 전부 `"pending"`이다. 게임 내 도감·소장고
  카드에 "검증 대기" 배지로 노출한다(척추 5번 — 데이터 신뢰도도 공개 대상).
- **(규칙, B8)** `sourceStatus: "pending"` 항목은 **드랍 풀에서 제외한다.** 배지는
  도감 상세의 출처 줄에만 노출되고, 감정 카드나 드랍 연출 어디에도 "아직 1차
  자료 대조 전"이라는 면책조항이 끼어들지 않는다 — 게임 최초의 재미 문장③
  ("이게 진짜 있는 물건이라고?")이 발생하는 순간에 검증 미완료 경고를 띄우면
  그 순간 자체가 훼손된다. 검증(`"verified"`)을 마친 항목만 드랍 대상이고,
  `"pending"` 항목은 데이터가 존재하되 세계 원장에는 아직 등재되지 않는다 —
  파이프라인이 검증을 마치는 대로 드랍 풀에 편입된다.
- **(규격, B8)** `note`(내력)는 **2~3문장**으로 쓴다. 한 문장은 "무엇인가"에
  그쳐 실존의 무게가 안 실리고, 4문장 이상은 카드 뒤집기 연출(§3.3)의 리듬을
  깬다. **T2~T4는 텍스트 밀도를 우선한다** — 상위 티어일수록 재미 문장③이
  걸리는 순간의 비중이 크므로(T3는 전체 정지 + 타이핑 연출), 사실 밀도가
  높은 문장(연대·소장 경위·특이점을 압축한 2~3문장)을 T0~T1보다 우선 작성한다.
  T0~T1은 1문장으로 줄여도 된다(§4 초기 `condition`처럼 티어 비례 자원 배분
  원칙과 같은 방향이다).

## 6. 라이선스 규칙 — 사실과 문장의 분리 (G7, 신규)

- **사실**(이름·연대·출토지·소장처·재질·규격 같은 메타데이터)은 저작권 대상이 아니다.
  출처에서 그대로 확인해 기록해도 된다.
- **문장**(`note`, `disputed`)은 사실을 근거로 **새로 쓴다.** 원문 복붙 금지.
  검증 가능한 형태의 규칙:

  ```
  NOTE_MAX_VERBATIM_RUN_WORDS = 8
  ```

  `note`의 어떤 부분도 출처 원문과 연속 8단어 이상 일치하면 안 된다. 이 규칙은
  n-gram 대조로 기계 검사가 가능하다(`scripts/validate-artifacts.mjs`, §7이 이름을
  확정한다 — 구현은 이 기획의 범위 밖).
- CC BY-SA 등 전파조건이 있는 출처(Wikipedia 등)는 **문장 인용에 쓰지 않는다.** 사실
  추출은 허용된다 — 사실은 저작권 대상이 아니다.

### 6.1 이미지 — v0.4 개정 (기존 금지를 뒤집는다, G72)

> ⚠️ **(v0.4 정정)** 이 절은 원래 "이미지 사용 모두 금지. 이미지는 어차피 절차적 도트
> 생성으로 대체돼 해당하지 않는다"고 적혀 있었다. **마지막 문장이 전제를 잘못 잡았다.**
> 도트 아이콘은 *게임 화면의 유물*이고 실사 이미지는 *"이게 진짜 있는 물건이라고?"의
> 증거*다. 둘은 대체 관계가 아니다 — 실존이 전제인 게임에서 증거를 스스로 금지하고
> 있었던 셈이다. 근거 전문은 `notes/decisions.md` G72.

**실사 이미지를 허용한다.** 도트 아이콘을 대체하지 않고, 상세 화면에서 "실제로는
이렇게 생겼다"를 보여 주는 보조 자료로만 쓴다.

허용 라이선스는 이 목록뿐이다(`ImageLicense`, `types.ts`):

| 라이선스 | 판정 | 근거 |
| --- | --- | --- |
| 퍼블릭 도메인(만료·포기·정부 저작물) | 허용 | 조건 없음 |
| CC0 1.0 | 허용 | 조건 없음 |
| CC BY 2.0 / 2.5 / 3.0 / 4.0 | 허용 | 저작자 표시만 요구 |
| **CC BY-SA (전 버전)** | **거부** | 전파조건 — 번들을 SA 조건으로 배포해야 한다는 해석을 감당해야 한다 |
| CC BY-NC · CC BY-ND | 거부 | 비상업·변경금지 |
| 공정이용(fair use) 근거 파일 | 거부 | 우리 쪽 이용이 그 근거 안에 들어가지 않는다 |
| 판정 불가 | 거부 | 모르면 안 쓴다(§1 원칙의 연장) |

지켜야 할 것:

1. **저작자 표시는 옵셔널이 아니다.** `ArtifactImage`의 `license`·`credit`·`sourceUrl`이
   필수 필드다. 표시 위치는 **상세 화면의 사진 바로 아래 캡션**이다 — 별도 크레딧
   페이지로 밀면 사진과 표기가 분리돼 실질적으로 표기하지 않은 것과 같아진다.
2. **런타임 외부 요청 금지는 그대로다.** 이미지는 `app/public/artifacts/`에 들어가
   번들에 복사된다. §7 원칙 6번("런타임은 이 파일만 읽는다")과 같은 규칙이다.
3. **번들 예산** — 파일당 96KB, 합계 4.5MB. `qa:artifacts`가 초과를 실패로 잡는다.
4. **수집은 두 단계다.** `--plan`이 후보를 떨어뜨리고 사람이 검수한 뒤 `--apply`가
   그 파일만 읽는다(§15). 검색 결과를 그대로 게임 데이터로 승격하지 않는다.
5. **종당 1장.** 여러 각도·상태의 사진을 모으는 것은 이 게임의 목적이 아니다.

## 7. 수집·검증 파이프라인 (네트워크 차단 환경 대응)

이 환경은 런타임뿐 아니라 **개발 세션도** 외부 네트워크가 차단돼 있다. 그래서 수집은
별도의 네트워크 허용 세션에서 일괄 수행하고, 그 결과만 레포에 커밋한다.

1. **수집**(네트워크 허용 세션): 거점별 §9 배분표를 기준으로 사실(이름·연대·출토지·
   소장처)을 1차 자료에서 찾아 `source` URL과 함께 초안에 적는다.
2. **검증**: `source` 개수 기준(§5)을 충족하는지 확인한다. T4는 독립 출처 2개.
3. **작문**: `note`를 사실 근거로 새로 쓴다(§6 규칙). `disputed`는 반환 논쟁이 실제로
   있는 항목에만 채운다.
4. **상태 배정**: §4의 `initialCondition` 공식을 적용하거나, 출처가 실제 손상을
   명시하면 override한다.
5. **커밋**: 결과를 `app/src/game/artifacts.ts`의 `Row` 튜플 형식(§2의 확장 필드
   포함)으로 레포에 커밋한다. 검증을 마친 항목만 `sourceStatus: "verified"`,
   나머지는 `"pending"`.
6. **런타임**: 이 파일만 읽는다. 이후 네트워크 접근이 전혀 없어도 빌드·플레이가
   가능하다(협상불가 항목 — 정적 산출물 — 을 그대로 지킨다).
7. **검증 스크립트**(`scripts/validate-artifacts.mjs`, 이름만 여기서 확정하고
   구현은 이번 기획의 범위 밖이다): 아래를 자동 검사한다.
   - 거점별 티어 개수가 §9 배분표와 일치하는가.
   - `source.length ≥ ARTIFACT_MIN_SOURCES`(T4는 `T4_MIN_INDEPENDENT_SOURCES`).
   - `id` 중복 없음, `condition` ∈ [0,4], `minLayer`가 그 거점 층수(12) 이내.
   - `note`가 `NOTE_MAX_VERBATIM_RUN_WORDS`를 넘는 연속 일치 구간 없이 작성됐는가
     (출처 원문 대조 n-gram 검사).

## 9. 기존 미검증 60점의 처리 방침 (G7)

`notes/decisions.md` G7의 결정: 기존 60점은 **480종 로스터의 시드로 재사용**하되,
`source` 필수 규칙을 소급 적용해 검증 전까지는 전부 `sourceStatus: "pending"`이다.
추가로 이 문서가 확정하는 건 **거점당 T4=1 쿼터와 기존 T4 8점(경주 3·룩소르 3·폼페이 2)의
충돌**을 어떻게 푸는가다. 8점을 그대로 두면 경주·룩소르가 쿼터를 초과한다.

**원칙**: 애매성이 있는 항목만 흔한 쪽으로 재분류한다(§1). 진짜 유일 개체인데 쿼터가
초과된 항목은 **거짓으로 등급을 낮추지 않는다** — 대신 이번 480종 로스터 밖으로
보류하고, 차기 확장(쿼터 상향 또는 거점당 복수 유일 규칙 도입 시) 후보로 남긴다.

| 거점 | 기존 T4 후보 | 최종 처리 | 근거 |
| --- | --- | --- | --- |
| 경주 | 금동미륵보살반가사유상 | **T4 유지** | 쟁점 없는 단일 개체 |
| 경주 | 훈민정음 해례본 | **T3로 재분류** | 상주본 존재 쟁점(기존 eval.md 결정 유지) |
| 경주 | 천마도 장니 | **T3로 재분류** | 유사 마구 장식이 다른 고분에서도 출토돼 개체 특정성이 낮음(애매성) |
| 룩소르 | 투탕카멘 황금 마스크 | **T4 유지** | 가장 상징적인 단일 개체 |
| 룩소르 | 로제타 석 | **보류(차기 확장 후보)** | 진짜 유일 개체이나 거점 쿼터 초과. 허위 하향 금지 |

쿼터 이하이므로 재분류가 필요 없고 추가 수집만 하면 된다(§8 표의 "현재 상태" 열).

이 표는 §3에 나온 대표 사례에 대한 처리이고, 같은 재정리 로직을 `app/src/game/artifacts.ts`
의 나머지 항목(이 문서의 §10은 60점 중 발췌라 전부를 담지 않았다)에도 파이프라인
실행 시점에 기계적으로 적용해야 한다 — 규칙(§1 애매성 판정, 쿼터 초과 시 보류)은
이미 확정됐으므로 나머지 적용은 사실 대조(네트워크 필요)의 문제일 뿐 기획 판단이
남아 있지 않다.

## 12. 확장 규칙 갱신

유물을 추가할 때 지켜야 할 것. v0.1의 4개 규칙에 v0.2가 3개를 더한다.

1. 현존 수량 근거를 `note`나 커밋 메시지에 남긴다.
2. T4를 늘릴 때는 **정말 하나뿐인지** 확인한다. 티어 인플레이션이 이 게임을 가장 빠르게
   죽인다. 거점당 T4 쿼터(`SPECIES_PER_SITE_BY_TIER[4] = 1`)를 초과하는 진짜 유일
   개체는 §9의 보류 규칙을 따른다 — 허위로 등급을 낮추지 않는다.
3. 권역·층 구성과 시대가 맞는지 확인한다. 조선 유물이 원삼국 층에서 나오면 안 된다.
4. 도감 완주는 이제 단일 엔딩 조건이 아니라 명성·순위 축(`notes/decisions.md` G4)의
   일부다 — `spec.md` §13.2(v0.2 엔딩·승리 조건, `notes/decisions.md` G13)를
   따른다(정정, B10 — "eval.md의 시즌 마일스톤 표"는 존재하지 않는 문서를
   가리키는 떠넘기기였다). v0.1의 도감 엔딩 조건은 **75%**다(`CODEX_GOAL=0.75`,
   `app/src/game/balance.ts`, spec.md §2.10 — 정정, 기존 "80%"는 오기였다.
   §2.10이 80%를 명시적으로 기각한 이유까지 참조). v0.2는 `CODEX_GOAL_V2=0.75`
   (480종 기준 360종)로 같은 비율을 유지한다.
5. **(신규, G7)** 모든 신규 종은 `source` 최소 1개(T4는 2개 독립 출처)를 채우기
   전까지 게임 데이터에 커밋하지 않는다. `sourceStatus: "pending"`으로 먼저 커밋하는
   것은 허용되지만, 출처 필드 자체가 비어 있으면 안 된다.
6. **(신규, G7)** `note` 작성 시 §6의 `NOTE_MAX_VERBATIM_RUN_WORDS` 규칙을 지킨다.
   출처 원문을 옮겨 적지 않는다.
7. **(신규, G6)** 신규 종의 `condition` 초기값은 §4의 공식으로 계산한다. 손으로
   임의의 값을 넣지 않는다 — 실제 손상 근거가 있을 때만 override하고 그 근거를 남긴다.

## 13. `balance.ts`/`types.ts` 반영 상수·타입 총람

```ts

export type SourceStatus = "verified" | "pending";
// Artifact 타입에 condition/source/sourceStatus 3필드 추가(§2)

// balance.ts 또는 game/artifacts.ts (신규, 이 문서 §4~§8)
```

## 14. v0.3 확대 — 280종 → 2000종 (파이프라인)

### 14.1 §7의 전제 정정

§7은 "개발 세션도 외부 네트워크가 차단돼 있다"고 적었다. **API는 맞지만 GitHub의
오픈액세스 덤프는 받을 수 있다**(`notes/decisions.md` G59의 측정표). 메트로폴리탄
미술관 `metmuseum/openaccess`(CC0 메타데이터, 392,483점)를 실제로 내려받아 이번
확대의 원천으로 썼다.

§7의 원칙 6번("런타임은 이 파일만 읽는다")은 그대로다 — 수집은 개발 시점에 끝나고
결과물만 레포에 들어간다.

### 14.2 파일 구성

### 14.3 어휘표가 곧 수집 필터다

`lexicon.mjs`에 없는 이름은 후보에서 **아예 빠진다.** 이 구조가 두 가지를 동시에
해결한다. (1) "파편(fragment)"·"조각(piece)"·"미상(undetermined)" 같은 카탈로그
부스러기가 도감에 들어오지 않는다. (2) 한국어 이름이 100% 채워진다 — 기계 번역이
아니라 유물 종류별로 손으로 고른 역어를 쓰기 때문이다. 그리스·로마 기형처럼
고유명인 것(킬릭스·레키토스·암포라)은 음차하고, 그 외는 한국 고고학 용례를 따랐다.

### 14.4 종의 정의와 티어 판정

- **종 = (거점, 어휘 키, 층 연대)**. 근거는 `notes/decisions.md` G60.
- **티어는 T0~T2만 자동 판정**, 메트 소장 점수를 현존 수량의 하한으로 쓴다.
  T3·T4는 파이프라인이 만들지 않는다 — 근거는 G61.

### 14.5 품질 분업 (중요)

생성 `note`는 메트의 구조화 필드에서 조립한 1~3문장이다. §6의 라이선스 규칙
(원문 연속 8단어 금지)은 지키지만, **손글씨 280종의 2~3문장과 질이 다르다.**

실존의 무게(재미 문장③)를 지는 건 여전히 손글씨 쪽, 특히 T3·T4다. 생성분은
수집의 양을 담당한다. 이 분업을 잊지 말 것 — "2000종 전부 같은 품질"이 아니다.

## 15. v0.4 — 실사화 (실사 디테일 + 실사 이미지)

### 15.1 무엇이 문제였나

v0.3 생성분의 `note`는 이렇다.

> 메트로폴리탄 미술관이 17~20세기로 편년한 두루마리다. 재질은 비단. 같은 종류가 이
> 컬렉션에만 99점 있다.

사실이다. 그런데 **이 물건이 왜 남았는지, 무엇이 특이한지**가 없다. §14.5가 "생성분은
수집의 양을 담당한다"고 분업을 적어 뒀지만, 양이 2,000종이 되고 나니 도감을 읽는
경험 자체가 조립문 읽기가 됐다.

### 15.2 필드를 나눈 이유

`note`는 **2~3문장 규격**이다(§5 B8) — 카드 뒤집기 연출의 리듬 때문이다. 실사
디테일을 여기에 밀어 넣으면 그 연출이 깨진다. 그래서 별 필드로 가른다.

```ts
export type ArtifactDetail = {
  specs?: { label: string; value: string }[];  // 계측·재질
  story?: string;                              // 왜 남았는지·무엇이 특이한지, 2~4문장
  provenance?: string;                         // 발견·소장 경위
  refs?: string[];                             // 문장 단위 근거 URL
  sourceStatus: SourceStatus;                  // §5와 같은 어휘
};
```

`Row` 튜플에는 넣지 않았다. 3,700줄짜리 손글씨 파일의 모든 행을 건드려야 하고,
이미지 쪽은 파이프라인이 덮어쓰는 생성 파일이라 성격이 다르다. 곁다리 표 두 개를
`artifacts.ts`가 id로 합친다:

| 파일 | 내용 | 누가 쓰는가 |
| --- | --- | --- |
| `app/src/game/details.ts` | 실사 디테일 40종 | 사람 |
| `app/src/game/images.generated.ts` | 이미지 메타데이터 | `scripts/fetch-images.mjs` |

### 15.3 UI — 접힌 상세, 드랍 연출은 건드리지 않는다

`ui/ArtifactDetail.tsx`가 **도감 상세와 소장고 상세에만** 붙는다. 드랍 연출
(RevealModal)은 이 컴포넌트를 쓰지 않는다. 기본 접힘이고, 사진·계측·내력·경위·출처
각 절이 독립적으로 옵셔널이다 — 이미지 0장에서도, 일부만 있어도 화면이 깨지지 않는다.

부수 효과: 상세 화면이 `source` 목록을 **처음으로** 노출한다. 척추 5번("규칙은
공개한다")이 데이터 신뢰도까지 포함한다는 §5의 취지가 그동안 화면에 없었다.

### 15.4 현재 커버리지

```
실사 디테일   40종 (T4 12 + T3 28), 전부 sourceStatus: "pending"
실사 이미지    0종
```

**디테일 40종이 전부 `pending`인 이유:** 이 세션은 외부 네트워크가 막혀 1차 자료를
열어 대조하지 못했다. 확신이 없는 수치·연도는 **적지 않았다** — 비워 두는 쪽이 틀린
숫자를 적는 쪽보다 낫다(§1 원칙). `refs`도 그 종의 `source`에 이미 들어 있던 실제
URL만 옮겼다.

**이미지 0종인 이유:** egress 프록시가 위키미디어를 CONNECT 403으로 막는다.

### 15.5 나머지를 채우려면

`scripts/README.md`의 "실사 이미지 수집" 절을 따른다. egress 허용 목록에 필요한 것:

```
commons.wikimedia.org
upload.wikimedia.org
```

실행:

```bash
node scripts/fetch-images.mjs --plan      # 후보 조회 → data/commons-images.candidates.json
#   candidates.json 을 사람이 검수
node scripts/fetch-images.mjs --apply     # 검수분만 내려받아 images.generated.ts 생성
pnpm --filter relic-king qa:artifacts
```

`data/commons-images.json`에 손글씨 T3·T4 40종의 영문 질의어가 들어 있다 — 커먼즈는
한국어 유물명으로 거의 잡히지 않기 때문이다. T2 146종은 `name + holder`로 검색한다.

디테일 텍스트의 검증(`pending` → `verified`)과 T2 146종 확장은 같은 세션에서 이어서
할 일이다. `--plan`이 커먼즈 파일 설명에서 계측값을 같이 긁어 오므로, `specs`의
1차 초안은 그쪽에서 나온다.
