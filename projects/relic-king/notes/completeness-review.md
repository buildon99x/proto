## 0. 결론

**v0.6은 1판이 지적한 "죽은 구간"을 실제로 살렸다. 그 대신 결정이 있어야 할 자리를
잡무가 채우고 있고, 압축된 16시간 판에 옛 시계들이 따라오지 못했다.** 첫 제보는 20초에
뜨고, 첫 원정은 경주에서 시작하며, 방치 10시간 동안 1시간 넘게 아무 일도 없는 구간이
45%에서 10.5%로 줄었다 **[실측]**. 엔딩은 140시간에서 16시간 29분이 됐다 **[실측]**. 여기까지는
분명한 진전이다.

남은 문제는 세 갈래다.

- **조작이 결정보다 많다.** 운영 플레이는 첫 10시간에 144회를 눌러야 하고, 그중 85회가
  발굴단 증강이다 **[실측]**. 20분~1시간 구간은 시간당 88.5회, 약 40초에 한 번이다.
  이제 방치형이 아니라 클릭 관리 게임에 가깝다 **[추론]**.
- **결정을 재는 자가 결정을 부풀린다.** `density`의 B축은 첫 10분 제보 4~5건을 모두
  "결정"으로 세지만, 그중 누를 버튼이 실제로 뜨는 것은 1~2건이다 **[실측]**. 게이트
  "첫 10분 결정 ≥5회"는 실제로는 넘지 못하고 있을 가능성이 크다 **[추론]**.
- **시계가 어긋났다.** 엔딩은 16시간인데 시즌은 12주이고(엔딩 화면에 "D-84"가 그대로다),
  인력 시장은 24시간마다 바뀐다. 그 결과 **같은 단장 "정민재"가 네 팀을 동시에 이끈다**
  (`v065-active-ending-dig.png`, §7 버그 2).

**다음에 할 일은 이 순서를 권한다.**

1. **발굴단 증강을 자동 재투자에 넣고, 남는 조작을 결정만 남기도록 추린다.** G80.1이
   "적용하지 않음"으로 남겨 둔 항목이다. 가장 많은 조작 하나를 없애는 일이라 비용
   대비 효과가 가장 크다. → §5.1
2. **16시간 판에 맞춰 시계를 전수 점검한다.** 시즌 길이, 인력 시장 갱신, 엔딩 뒤에 오는
   것을 한 번에 정한다. 같은 단장 중복 고용은 그 전에 바로 고친다. → §5.2
3. **절정 연출을 채우면서 v0.7 세계관의 첫 장치를 화면에 올린다.** 유일 획득 모달의
   이름 공개, 엔딩 한 장, 그리고 v0.7.1이 "가장 싼 장치"라고 적은 "마지막 확인" 문구다. → §5.3

그리고 **모바일 제보 배너가 깨져 있다**(§7 버그 1). 첫 제보가 20초에 뜨니, 모바일 사용자가
처음 보는 화면이 이 배너다. 위 세 가지보다 먼저 고칠 일이다.

## 3. 현재 완성도 — 경험 기준

### 3.1 제보 레이스: 이제 긴장은 있다. 결정은 절반이다

v0.6의 반응 유예, v0.6.1의 결판, 배너의 승산 표시("승산 62%(경쟁 1명) · 안목 +48%")는
문장 ②를 처음으로 화면에 세웠다. 25초 시점 배너에 [집중 굴착] 버튼이 뜬다
(`v065-fresh-25s-tip.png`). 레이스 승률은 방치·운영 모두 약 79%다(방치 10시간 134승 35패,
운영 148승 39패) **[실측]**. 1판의 84~93%보다 낮아 긴장이 성립하는 대역에 들어왔다 **[추정]**.

하지만 **버튼이 뜨는 비율**은 구간마다 다르다 **[실측]**.

| 구간 | 방치: 제보 / 버튼 있음 | 운영: 제보 / 버튼 있음 |
| --- | --- | --- |
| 첫 10분(5시드) | 4~5 / 1~2 | 4~5 / 1~2 |
| 첫 1시간 | 20 / 2 | 19 / 5 |
| 첫 10시간 | 173 / 98 | 190 / 160 |

버튼이 없는 제보는 직접 발굴이 그 거점을 파는 경우다. 이때 배너는 "직접 발굴이 이
자리에서 쫓는 중 — 적중 28%"라고 적을 뿐, 누를 것이 없다 **[코드]**(`TipBanner.tsx`).
그리고 [급파]는 10시간 동안 **한 번도** 뜨지 않았다. 자동 순회가 팀을 쉬게 두지 않기
때문이다 **[실측·추론]**. 기능은 있는데 화면에 나오지 않는 버튼이다.

**계측 자가 이 차이를 가린다.** `density`의 결정 감시자는 `playerCanReactAt()`이 참이면
제보를 결정으로 센다(`app/src/sim/density.ts:132`). 그런데 그 함수는 `w.activeSite === site`,
즉 직접 발굴만 있어도 참이다(`engine.ts:2130`). 그래서 첫 10분에 결정 6~7회(그중 제보 4~5)로
찍히지만, 버튼 기준으로 다시 세면 제보 결정은 1~2회다. 게이트 "첫 10분 결정 ≥5회"를
버튼 기준으로 다시 재야 한다. `eval.md` §28.8이 이미 "정책이 제보 버튼을 누르지 않는다"를
다음 패스 1순위로 적어 뒀는데, 정책보다 먼저 **자의 정의**를 고쳐야 그 패스가 의미 있다.

### 3.2 페이싱: 운영은 살아 있고, 방치는 10시간 뒤에 다시 식는다

| 구간(시간당) | 방치 의미 사건 | 운영 의미 사건 | 운영 사람 조작 |
| --- | ---: | ---: | ---: |
| 0~20분 | 315 | 417 | 24 |
| 20분~1시간 | 177 | 192 | **88.5** |
| 1~6시간 | 97 | 209 | 10.8 |
| 6~10시간 | 42.5 | 60.5 | 5.8 |

(출처: `playlog --hours 10` **[실측]**)

운영 플레이는 10시간 동안 15분 이상 공백이 0%다. 방치 플레이는 10시간까지는 괜찮지만,
24시간으로 늘리면 1시간 이상 공백이 24.5%, 최장 2시간 19분이 된다 **[실측]**. 그리고 방치로는
24시간에 도감 690/1,902종(36%)이라 **엔딩에 닿지 않는다** **[실측]**. brief 핵심 가치의
"방치만으로도 완주할 수 있다"(`brief.md:221`)는 v0.5에서도 v0.6에서도 성립하지 않는다.
척추 4번의 "클릭"이 삽질 클릭만 뜻한다고 AGENTS.md가 정의해 두긴 했지만, brief 문장은
그렇게 읽히지 않는다. 문장을 고치든 게임을 고치든 둘 중 하나는 해야 한다.

### 3.3 조작: 결정이 아닌 클릭이 하루 345회

운영 플레이 첫 10시간의 사람 조작은 144회·313단계다. 하루로 환산하면 345.6회다 **[실측]**.
구성은 발굴단 증강 85회, 박물관 확장 16회, 전시 15회, 보관소류 12회 순이다. 증강은
"살 수 있으면 산다" 외에 판단이 끼지 않는 조작이다 **[추론]**. v0.6.0 changelog도 이걸
"남은 것"으로 적었고, G80.1은 v0.3.4 때부터 "적용하지 않음"이다.

brief의 관여 예산은 하루 2~3회 방문이다. v0.6의 16시간 판에서 이 예산을 문자 그대로
적용할 필요는 없지만, **40초에 한 번**은 어떤 해석으로도 방치형의 리듬이 아니다.
Kittens Game의 원칙("처음엔 어렵게, 나중에 업그레이드로 해결")에 비춰 보면, 증강은
처음 몇 번만 손으로 하고 곧 자동화가 보상으로 와야 할 자리다(원본 §3.5).

### 3.4 화면에서 본 것

- **첫 화면은 좋아졌다.** 1팀이 경주 현지에 있고, 1.5초 시점 발굴력 "5.7/s(1팀)"이다
  (`v065-fresh-00-first.png`). 1판의 "2118:59 후 도착"은 사라졌다.
- **그런데 1.5초에 "더 올려도 소용없다"가 뜬다.** 같은 화면 하단에 "경주의 드랍 간격이
  하한 16초에 닿았다 — 여기서 발굴력을 더 올려도 드랍 수는 그대로고 층만 빨리
  내려간다"가 이미 떠 있다. 게임 시작 1초에 가장 먼저 보이는 업그레이드 버튼(인부
  $1.8만)의 효과를 반쯤 부정하는 문장이다. 규칙 공개는 좋지만, 첫 1분에는 "층이 빨리
  내려간다"만 말하는 편이 맞다 **[추론]**.
- ~~본거지 선택은 175초에 뜬다~~ **(정정, 2026-09-24)** 85초 캡처에 이미 떠 있다. 이 모달은
  첫 감정 순간(엔진 약 36초)에 열린다(`ui/useGame.ts`의 `setOnboardingPending`). 175초 캡처만
  보고 판단한 오류였다. 게다가 모달이 **첫 제보 레이스 위에 덮인다.** 85초 캡처에서 모달 뒤
  배너가 "확보 — 먼저 도달했다"로 끝나 있다. 첫 승리를 가르치는 순간이 모달에 가려진다.
  상세는 `notes/decision-tree-10h.md` §2.
- **안목 막대가 도감에 섰다**(`v065-idle-5h-codex.png`). "이 거점 안목 98% · 제보 선점 +59%".
  도감이 무언가를 바꾼다는 것이 한 줄로 보인다.
- **엔딩은 여전히 한 줄이다.** "도감을 채우고 종합 순위 1위에 올랐다 — 유물왕. 발굴은
  계속된다." 그 위에 제보 배너가 그대로 돌고, 헤더의 시즌은 "D-84"다
  (`v065-active-ending-dig.png`). 끝났다는 신호도, 다음에 무엇이 오는지도 없다.
- **유일 획득 모달이 배너와 모순된다.** 배너에는 "금동미륵보살반가사유상(국보 83호) 유일"이
  이름째 떠 있는데, 모달은 "이름과 내력은 감정이 끝나면 공개된다"고 적는다
  (`assets/screenshots/play/01-unique-acquired.png`). 참고로 이 스크린샷은 합류 전 ₩ 빌드에서
  찍혀 헤더가 "125억 ₩"이다. `play`를 다시 돌려 갱신할 필요가 있다.
- **모바일 제보 배너가 깨진다**(`v065-mobile-20s.png`, §7 버그 1).

## 5. 약점과 개선 방향 — 우선순위순

비용은 상대 규모다(S = 하루 안, M = 며칠, L = 한 릴리스).

### 5.0 [즉시] 모바일 제보 배너와 같은 단장 중복 고용

버그라 우선순위 목록과 따로 둔다. 둘 다 S다. 상세는 §7.

### 5.1 [1순위] 발굴단 증강을 자동화하고, 조작을 결정만 남긴다

**근거.** §3.3. 첫 10시간 조작 144회 중 85회가 증강이고, 20분~1시간에 시간당 88.5회다 **[실측]**.

**방향.** 증강(`buyTeamWorker`·`buyTeamGear`)을 자동 재투자 대상에 넣는다. 첫 한두 번은
손으로 하게 두고, 그 뒤 "자동 증강"을 켜는 토글을 보상처럼 보여 준다(Kittens식). 박물관
확장·보관소도 같은 기준으로 본다. **남겨야 하는 조작은 기회비용이 있는 것뿐이다.** 원정지
선택, 제보 대응, 거점 해금, T3 이상의 쥐기/팔기가 여기에 든다.

**기대 효과.** 하루 환산 조작이 345회에서 두 자릿수로 준다 **[추정]**. 조작 중 결정의 비율이 오른다.

**비용.** S~M. 자동 재투자 루프에 항목 하나를 넣고 설정 토글 하나를 붙이는 일이다.

**부작용.** 자동화하면 운영 플레이와 방치 플레이의 격차가 줄고, 방치 플레이가 엔딩에 가까워진다.
§3.2의 brief 문장 문제가 그만큼 풀린다. 대신 엔딩 시각이 앞당겨질 수 있으므로 `sim --hours 48`로
확인한다.

**확인.** `playlog --hours 10`의 "사람이 눌렀어야 할 조작" 합계와, 그중 기회비용 있는 조작의 비율.

### 5.2 [2순위] 16시간 판에 맞춰 시계를 전수 점검한다

**근거.** v0.6이 판을 8.6배 압축했지만 따라오지 않은 상수가 있다 **[코드]**.

| 시계 | 값 | 16시간 판에서 생기는 일 |
| --- | --- | --- |
| `SEASON_LENGTH_WEEKS` | 12주 | 엔딩 화면이 D-84. 시즌 롤오버(프레스티지)는 엔딩 뒤 83일 |
| `STAFF_MARKET_REFRESH_HOURS` | 24시간 | 한 판 동안 후보가 한 번도 안 바뀐다. 같은 사람을 반복 고용(§7 버그 2) |
| 보존 판정 격자 | 2.8시간(v0.6.3에서 고침) | 고쳐진 사례. 이 방식을 다른 시계에도 적용한다 |

v0.6.3은 보존 저하가 한 판에 한 번도 안 일어나던 문제를 이 방식으로 찾아 고쳤다. **같은 종류의
결함이 더 있다는 뜻이다.** `balance.ts`에서 시간 단위(`_HOURS`, `_DAYS`, `_WEEKS`)가 붙은 상수를 전부
뽑아, 16시간 판에서 몇 번 도는지 표로 만든다.

**가장 큰 설계 질문은 엔딩 뒤다.** 지금은 16시간에 "발굴은 계속된다"가 뜨고, 그 뒤로 할 일이
정의돼 있지 않다. 권고안은 **엔딩 = 시즌 롤오버의 시작**이다. 명예의 전당 헌정과 다음 시즌의
이월 보너스(`SEASON_CARRYOVER_*`)가 이미 코드에 있다. Paperclips의 단계 전환처럼 엔딩이 새 판의 문을
열게 하면, 새 시스템 없이 장기 꼬리가 생긴다. 그러려면 시즌 길이를 판 길이에 맞추거나, 엔딩이
시즌을 조기 종료시키게 해야 한다.

**비용.** M. **부작용.** 시즌을 줄이면 명성·관람객처럼 누적형 축의 균형이 바뀐다. 3축 순위를 다시 잰다.

### 5.3 [3순위] 절정 연출과 v0.7 첫 장치를 함께 올린다

**근거.** §3.4. 유일 모달의 이름 비공개와 배너와의 모순, 엔딩 한 줄, 소리 없음.

**방향.**
1. 레이스로 얻은 유일은 그 자리에서 이름과 내력을 보여 준다. 배너가 이미 이름을 말하므로
   숨길 이유가 사라졌다.
2. 같은 모달에 v0.7.1이 적은 **"마지막 확인: 국립경주박물관, 2094년 3월"** 한 줄을 붙인다.
   데이터의 소장처에 해체 연도 상수 하나를 더하는 일이라, v0.7 서사 장치 여섯 가운데 가장
   싸다(changelog 0.7.1). 문장 ③("진짜 있는 물건")이 "진짜 있던 집"으로 가는 첫 화면이 된다.
3. 엔딩을 한 장짜리 기록으로 만든다. 걸린 시간, 가진 유일, 놓친 유일과 가져간 라이벌, 그리고
   다음 시즌으로 가는 버튼(§5.2)이 들어간다.
4. 소리는 Web Audio 합성으로 제보 시작·결판·유일 획득·엔딩 네 곳에만 둔다. 외부 리소스 0 규칙과
   충돌하지 않는다.

**비용.** S~M. 밸런스는 건드리지 않는다. **확인.** `play`의 `unique` 시나리오에 "모달에 이름이
보인다" 단언을 추가한다.

### 5.4 [4순위] 제보 결정을 정직하게 재고, [급파]를 살린다

**근거.** §3.1. 계측 자가 버튼 없는 제보를 결정으로 센다. [급파]는 10시간에 0회다.

**방향.** 먼저 `density`의 결정 감시자를 **화면에 버튼이 뜰 때만** 세도록 고치고 B축을 다시 잰다.
`TipBanner.tsx`의 `findReaction()`과 같은 조건을 쓰면 된다. 그다음 직접 발굴 제보에도 행동을 준다.
1판 권고(자금으로 승산을 산다)가 여전히 가장 싼 안이다. 핵심 딜레마인 팔면 강해지고 순위가
떨어진다는 긴장이 레이스에 바로 걸린다. [급파]는 자동 순회가 제보 중인 거점 근처의 팀을
"대기"로 남겨 두는 규칙이 없으면 뜰 수 없다. 살릴지, 버튼을 지울지 정한다.
[집중 굴착] 버튼에는 대가(원정비 2배)를 금액으로 적는다.

**비용.** S(계측) + M(행동 추가). **부작용.** B축 수치가 내려가 게이트가 실패할 것이다. 그것이 이
항목의 목적이다.

### 5.5 [5순위] 세트 목표와 판매 결정

1판 §5.2·§5.5의 권고는 그대로 유효하다. 안목이 도감의 되먹임을 절반 채웠으므로 우선순위를
내렸다. 세트(5~8종 실제 역사 묶음)는 3.5시간 이후의 중간 목표를 만들고, 세트 구성품이 자동 매각
대상에 끼면 판매를 다시 결정으로 만든다. v0.6.4가 중복 자동 정리를 기본으로 켰으므로, 이 결정
카드는 **T3 이상과 세트 구성품**으로 좁게 둬야 새 잡무가 되지 않는다.

## 8. 재현

```bash
pnpm --filter relic-king playlog -- --hours 10 --bucket 10
pnpm --filter relic-king playlog -- --hours 24 --bucket 60
pnpm --filter relic-king density
```

제보 순간의 버튼 유무 프로브다. `app/src/sim/`에 임시 파일로 두고 `npx tsx`로 돌렸고,
커밋하지 않았다. "버튼 있음"은 현지 작업 중인 팀이 있거나 유휴 팀이 있는 경우다. [급파]에는
압축 이동 4시간 이내 조건이 더 붙으므로 상한값이다.

```ts
import { advance, createPersistentRecord, createWorld, grantStartingTeam, playerCanReactAt, runAutoRoutine } from "../game/engine";
import { actExpansion, liquidateSurplus } from "./policy";
const SEEDS = Array.from({ length: 5 }, (_, i) => 20260917 + i * 7919);
for (const mode of ["active", "idle"] as const) {
  const rows: string[] = [];
  for (const seed of SEEDS) {
    const w = createWorld(seed, false); grantStartingTeam(w);
    const rec = createPersistentRecord(); let acc = 0; let last: string | null = null;
    let react = 0, button = 0, all = 0;
    while (w.t < 600) {
      if (mode === "active") { liquidateSurplus(w); runAutoRoutine(w); actExpansion(w); }
      else { acc += 1; if (acc >= 60) { acc = 0; runAutoRoutine(w); } }
      advance(w, 1, false, 1, rec);
      const tip = w.tip; const key = tip ? `${tip.artifactId}@${tip.site}` : null;
      if (tip && key !== last) {
        all++;
        if (playerCanReactAt(w, tip.site)) react++;
        if (w.teams.some((t) => (t.status === "on_site" && t.targetSite === tip.site) || t.status === "idle")) button++;
      }
      last = key;
    }
    rows.push(`${all}/${react}/${button}`);
  }
  console.log(mode, "첫10분 제보/density가 결정으로 센 수/버튼 있음:", rows.join("  "));
}
```

결과: 운영 `5/5/1 4/4/2 4/4/2 4/4/2 4/4/2`, 방치 `4/4/1 4/4/2 4/4/2 5/5/1 4/4/2`.
1시간·10시간 값은 같은 루프를 `STEP_EARLY`/`STEP_LATE` 스텝으로 늘려 얻었다.

화면 캡처는 `app/dist`를 로컬 HTTP로 띄우고 Playwright로 찍었다. 시점별 세이브는 위 정책 루프로
