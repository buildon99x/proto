# 플레이 변화 보고서 (작업 브랜치 전·후)

한 브랜치의 작업이 **첫 1분·첫 10분의 경험**을 어떻게 바꿨는지를 재서 한 페이지로 보여 준다.
이 스킬의 핵심은 그림이 아니라 **공정한 비교**다. 전·후를 같은 자로, 같은 시드로, 오늘 다시 잰다.
옛 문서의 숫자를 옮겨 적으면 자가 달라서 비교가 성립하지 않는다(AGENTS.md "전 값은 그 자로
직접 재라"). 실제로 2026-09-24에 eval §27의 v0.5.1 값(3종·4종)과 오늘 잰 값(2종·3종)이 달랐다.

전체 소요는 30~40분이다. 거의 전부 측정이라 **백그라운드로 돌리고** 기다리는 동안 사용자에게
진행 상황을 짧게 알린다.

작업 폴더(`WORK`)는 세션 스크래치패드 아래에 둔다. 레포에는 아무것도 쓰지 않는다 —
스크린샷·빌드·측정 결과가 레포에 떨어지면 커밋되지 않은 변경이 생기고 stop 훅이 멈춘다.

```
S=projects/relic-king/.claude/skills/play-delta-report/scripts
WORK=<스크래치패드>/play-delta/<AFTER_REF>
```

## 1. 무엇과 무엇을 비교할지 정한다

```
eval "$($S/resolve_refs.sh [브랜치])"     # MODE · BASE_REF · AFTER_REF · *_LABEL · *_SUBJECT
```

기본 규칙은 **"이 브랜치가 main에 무엇을 더했나"**다.

- 이미 머지됐으면 그 머지 커밋과 머지 직전 main(`머지^1`)을 비교한다. 병렬로 들어온 다른
  작업이 양쪽에 똑같이 들어 있어서 이 브랜치의 효과만 남는다.
- 아직 안 머지됐으면 브랜치 끝과 main과의 merge-base를 비교한다.

사용자가 "브랜치 시작부터 끝까지"를 원하면 `--base <출발 커밋>`을 직접 준다. 두 기준은
결과가 다를 수 있다 — PR #33은 기본 규칙이면 v0.5.4 → v0.6.5, 출발점 기준이면 v0.5.1 → v0.6.5다.
어느 쪽으로 쟀는지 보고서 첫머리(`meta.json`의 `beforeRef`)에 적는다.

## 2. 양쪽을 워크트리로 준비한다

```
$S/prepare_side.sh $AFTER_REF $WORK/wt-after
$S/prepare_side.sh $BASE_REF  $WORK/wt-before
```

각 커밋을 워크트리로 꺼내 **그 커밋 자신의 코드로** 앱을 빌드한 뒤, 지금 체크아웃의 계측기
(`density.ts`·`telemetry.ts`·`play.mjs`·`harness.mjs`)를 양쪽에 덮어쓴다. 옛 엔진에 계측기가
부르는 함수가 없으면 알려진 읽기 전용 심을 자동으로 붙이고, 1시드로 시험 실행해 원장 몇 줄을
찍는다.

- `READY`가 나오면 다음으로 간다.
- `SHIM_NEEDED`(종료 코드 2)가 나오면 `references/shims.md`를 읽고 손으로 심을 단다.
- 어느 경우든 **기준 쪽 첫 제보 시각을 그 버전의 기록값과 대조한다.** 맞으면 이식이 된 것이다.
  안 맞으면 심이 동작을 건드렸다는 뜻이니 측정으로 넘어가지 않는다.

## 3. 잰다 (백그라운드, 순차)

```
$S/measure.sh before $WORK/wt-before $WORK --seeds 12 --ui-runs 3 [--sim-hours H]
$S/measure.sh after  $WORK/wt-after  $WORK --seeds 12 --ui-runs 3 --suite --sim-hours 48
```

두 줄을 한 백그라운드 명령에서 **차례로** 돌린다. `play`는 포트를 고정해 쓰므로 둘을 동시에
돌리면 서로 죽인다.

- **시드는 12**다. 첫 10분은 시드 흔들림이 가장 커서 5시드로는 최악값을 말할 수 없다(AGENTS.md).
- **UI는 3회**다. 한 걸음만 크게 흔들리면(v0.5.1 제보 배너 876~937초) 그 이유를 서술에 적는다.
- **엔딩 시간**은 합류·밸런스 변경이 있었으면 반드시 비교 쪽을 다시 잰다(PR #33은 관람료 변경으로
  16시간 25분이 16시간 1분이 됐다). 기준 쪽 엔딩이 수십 시간이면 `--sim-hours`를 그만큼 주거나,
  기록값을 쓰고 출처를 `meta.ending.note`에 적는다.

UI 실측은 `measure.sh`가 `tsx`로 돌린다. `node tests/e2e/play.mjs`로 직접 돌리면 시나리오가
TS 상수를 못 읽어 일부가 `undefined`로 통과하거나 통째로 죽는다(97/109로 나왔던 적이 있다).

## 4. 데이터를 모은다

```
python3 $S/build_data.py $WORK      # → report-data.json, ui-data.json (요약을 화면에 찍는다)
```

중앙값은 계측기와 같은 규칙(12개 중 낮은 쪽 가운데 값)으로 잡는다. 규칙이 다르면 표(계측기
출력)와 차트가 같은 축에서 다른 숫자를 말한다 — 첫 판에서 거점 해금이 표 3분 15초, 차트 3분
46초로 어긋났었다.

## 5. 문장을 쓴다 — `meta.json`, `narrative.json`

숫자는 전부 데이터 파일에서 나오고, **문장은 이 두 파일에만** 쓴다. 템플릿에는 특정 버전의
문장이 없다. 예시는 `references/example/`(PR #33, v0.5.1 → v0.6.5)이다. 형식은 그 파일을 그대로
따르고, 내용은 이번 측정값으로 새로 쓴다.

`narrative.json` 키와 들어갈 자리:

| 키 | 자리 | 무엇을 쓰나 |
| --- | --- | --- |
| `h1` | 제목 | 가장 큰 변화 하나. `<span class="from">`·`<span class="to">`로 전·후 값 강조 |
| `lede` | 머리말 | 결론부터. 무엇이 어떻게 달라졌고 원장 통과가 몇 → 몇인지 |
| `lanes` · `reach` · `ratio` | 각 차트 설명 | 차트를 어떻게 읽는지 + 거기서 보이는 사실 하나 |
| `uiSub` · `ui` | UI 절 설명 · 아래 메모 | 측정 방법 / 회차 편차와 그 이유, 시뮬 값과 다른 이유 |
| `cost` · `cliff` | 치른 값 | 엔딩이 줄었는지, 지루한 구간이 어디로 갔는지 |
| `ledgerActive` · `ledgerIdle` | 원장 표 아래 | 계산된 통과 수 뒤에 붙는 해석 |
| `suite` | UI 전체 검사 | (선택) 비교 쪽 검사가 무엇을 덮었는지 |
| `method` | 어떻게 쟀나 | 자, 두 커밋, 붙인 심과 재현한 기록값, **기록과 다른 값**, 재지 못한 것 |

`meta.json`: `beforeLabel` · `afterLabel` · `beforeRef` · `afterRef` · `date` · `ending{before, after, note}` ·
`recorded{firstT4Encounter, firstSiteUnlock}`(기준 쪽이 60분 안에 못 닿았을 때의 기록값, 선택) ·
`title`(선택. 같은 보고서를 갱신할 땐 첫 게시 제목을 유지).

문장 규칙 — 사용자 선호이기도 하다.

- **결론 먼저.** 머리말 첫 문장이 "무엇이 달라졌나"에 답한다.
- **데이터에 없는 주장을 하지 않는다.** 원인을 확인하지 않았으면 "(추정)"이라 쓰거나 "원인은
  확인하지 않았다"라고 쓴다. 기록값과 다른 값이 나오면 숨기지 말고 `method`에 적는다.
- **재지 못한 것은 못 쟀다고 쓴다.** 빠진 절이 있으면 그 이유와 함께 `method`에 남긴다.
- 한국어 문장 위생: 한 문장에 한 뜻, 능동태, 짧게. 표·차트 설명에 수식어를 쌓지 않는다.

## 6. 굽고, 한 번 보고, 올린다

```
python3 $S/render.py $WORK <스크래치패드>/play-delta-<AFTER_REF>.html
node $S/snapshot.mjs <그 html> $WORK          # snapshot-light-desktop.png · snapshot-dark-mobile.png
```

스냅샷은 **한 번만** 보고, 이름표 겹침·잘림·빈 차트 같은 눈에 보이는 결함만 한 번에 고친다.
템플릿을 고쳤다면 그것은 다음 보고서에도 남는 개선이니 스킬 쪽 `assets/report.tpl.html`을 고친다.

게시는 Artifact 도구 규칙을 따른다(새 보고서면 quickstart부터). 같은 브랜치의 보고서를 다시
굽는 경우라면 같은 파일 경로로 다시 게시해 URL을 유지한다.

## 7. 알린다, 치운다

사용자에게는 결론 한두 문장 + 링크 + 기록과 달랐던 값·재지 못한 것을 짧게 전한다.
보고서는 비공개로 올라가므로 팀과 보려면 Share 메뉴에서 공유해야 한다는 것도 알린다.

```
git worktree remove --force $WORK/wt-before; git worktree remove --force $WORK/wt-after
```
