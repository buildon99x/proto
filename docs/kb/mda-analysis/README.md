# docs/kb/mda-analysis — MDA 역기획 자산

> **목적:** 신규 프로젝트의 설계 근거를 만들기 위해 실존 게임을 MDA + Design Contract 4층으로 역기획하고, 그 결과를 **재사용 가능한 케이스**로 축적한다.
> **위상:** 지식베이스(KB). 코드 변경 없음. `docs/kb/concept-planning/`이 *컨셉 단계*의 기준선이라면, 이 폴더는 *메커닉·루프·체감 설계 단계*의 기준선이다.
> **언어:** 한국어.
> **갱신일:** 2026-09-14.

---

## concept-planning과의 분업

| 질문 | 담당 |
|---|---|
| 이 컨셉이 시장에서 살아남는가 | `docs/kb/concept-planning/` (후크·X+Y·30초 데모·레드플래그) |
| 이 게임을 어떤 메커닉으로 조립하고, 그 결과 플레이어가 무엇을 느끼는가 | **이 폴더** (Mechanics → Dynamics → Aesthetics + Contract) |
| 이 프로젝트를 실제로 무엇으로 만들 것인가 | `projects/{slug}/brief.md` · `spec.md` · `eval.md` |

컨셉 통과 → MDA 역기획 → brief/spec 작성 순서를 권장한다. 역기획 없이 spec을 쓰면 "무엇을 만들지"는 정해지지만 "왜 그 선택인지"의 근거가 비어 eval 기준을 세울 수 없다.

## 출처 규약

분석 스킬(`game-design-mda-analysis`)의 4-Tier 체계를 그대로 쓴다. repo의 `[H]/[M]/[L]` 규약과는 아래처럼 대응한다.

| Tier 라벨 | 정의 | repo 대응 |
|---|---|---|
| `[공식·T1]` | 개발자 본인 발언 (공식 블로그·강연·본인 인터뷰) | `[H]` |
| `[공식·T2]` | 공신력 매체의 개발자 직접 인용 | `[H]` |
| `[해석:합의·T3]` | 3자 매체·학술·Wikipedia 분석 | `[M]` |
| `[체감·T4]` | 커뮤니티·포털·유저 위키 | `[L]` |
| `[집계-A]` / `[집계-B]` | 공식 / 비공식 집계 수치 | `[H]` / `[M]` |
| `[해석:개인]` | 분석가 독자 해석 | `[L]` |

**`[공식]` 자격은 T1~T2만.** 3자 매체를 "공식"으로 표기하지 않는다.

## 케이스 추가 기준

아무 게임이나 케이스화하지 않는다. 아래를 모두 충족할 때만 파일을 만든다.

1. 진행 중이거나 예정된 `projects/{slug}` 하나 이상에 직접 근거가 된다.
2. 분석 결과가 **설계 결정으로 번역 가능**하다 — "무엇을 지키고 무엇을 바꾼다"가 나온다.
3. Tier 1~2 소스가 없다면 **정합률과 한계를 본문에 명시**한다. 명시하면 케이스화해도 되지만, 명시 없이 단정하면 안 된다.

## 필수 섹션

`# 게임명` → `한 줄 포지셔닝` → `전제` → `Core info` → `MDA layers`(Blueprint/Mechanics/Interface) → `Dynamics`(루프·창발·역전) → `Experience`(축 매핑·축군) → `약점·성취 양면` → `Design Contract` → `순설계 이식` → `인사이트` → `한계와 정합률` → `메타데이터(YAML)`.

`약점·성취`는 각 3~5개를 **반드시 양쪽 다** 채운다. 한쪽만 채운 문서는 편향된 문서다.
